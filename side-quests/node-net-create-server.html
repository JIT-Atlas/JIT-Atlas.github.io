§ 0 · The Short Answer FirstOne thread, sleeping in epoll_wait

This lesson takes the skeleton from Part 5 and changes one critical thing: the path through libuv is not the worker pool anymore. Sockets do not block worker threads. Sockets use the kernel's readiness machinery — epoll on Linux, kqueue on macOS/BSD, IOCP on Windows — and the main JS thread itself is the one that sleeps in epoll_wait.

We will trace this program:

JavaScript the program we trace 
const net = require("net");

const server = net.createServer((socket) => {
  socket.on("data", (chunk) => {
    socket.write("you sent: " + chunk);
  });
});

server.listen(3000);

…all the way from your JavaScript text down to the network interface card and back up to your 'connection' and 'data' event handlers.

When a Node TCP server is running, three things are true at once:

  1. The main JS thread is the only thread executing your JavaScript.
  2. That same main JS thread is also the thread sleeping in epoll_wait (or kqueue / IOCP) waiting for socket events.
  3. No libuv worker thread is involved in plain TCP I/O — not for accept, not for read, not for write.
!
Lock this in
fs.readFile uses libuv's worker pool because filesystem syscalls don't have a great non-blocking story. TCP sockets use libuv's event loop + readiness APIs because the kernel is happy to tell us "this socket has bytes ready" without anyone having to block.

The whole point of this lesson is to internalize that distinction. Same Node, same libuv, same main JS thread — completely different machinery underneath.

§ 2 · CPU and Threads — the Network AngleThe CPU never understood "the internet"

You already know from Part 5: a CPU executes machine instructions, a process is a resource container, a thread is an execution path. Nothing about networking changes that.

What the CPU still does not understand:

  • TCP connections
  • ports
  • IP addresses
  • HTTP
  • "the internet"

These are abstractions built on top of the kernel's networking subsystem, which itself is just code running on the CPU like everything else.

!
Lock this in
When a packet "arrives," what physically happens is: the NIC raises an interrupt, the CPU jumps into a kernel interrupt handler, and that handler is just more machine code running on some thread (often a softirq context). There is no "network event" the CPU directly perceives.

§ 4 · TCP from First PrinciplesReliable, ordered, byte-stream — and the kernel does the handshake

TCP is a reliable, ordered, byte-stream protocol over IP. Three properties matter for our lesson:

  1. Connections are explicit. A TCP connection is a 4-tuple (local IP, local port, peer IP, peer port) that both ends agree exists.
  2. The 3-way handshake establishes the connection: SYN → SYN-ACK → ACK.
  3. Bytes are buffered in the kernel on both ends. The application reads and writes into kernel-side buffers; the kernel handles retransmits, ordering, and flow control.

The handshake, drawn

Client                                  Server
  │                                       │
  │── SYN  (seq=X)                      ─▶│
  │                                       │  put on SYN queue (incomplete)
  │◀─ SYN-ACK (seq=Y, ack=X+1)          ──│
  │                                       │
  │── ACK  (ack=Y+1)                    ─▶│
  │                                       │  move to ACCEPT queue (complete)
  │                                       │
  │   connection ESTABLISHED              │
  │                                       │

The crucial point: the kernel completes the entire handshake by itself, before your accept() call ever runs. By the time you "accept," the connection already exists in the kernel's accept queue.

accept() doesn't create a connection. It pops an already-completed connection off the kernel's accept queue and gives your process a new fd for it.

§ 6 · Non-blocking SocketsThe flag that makes the event loop possible

A socket fd has a flag: O_NONBLOCK. With it set, every syscall on that fd has a new contract:

  • If the operation can be completed immediately, do it and return.
  • If it would have to wait, don't sleep — return immediately with EAGAIN / EWOULDBLOCK.

Non-blocking read()

▸ nonblock-read.txtO_NONBLOCK set
read(fd, buf, n) on a non-blocking socket:

  ┌── data in recv buffer? ───── YES → copy bytes, return n
  │
  └─────────────────────────────  NO → return -1, errno=EAGAIN
                                       (do NOT sleep the thread)

Compare to blocking read() (the Part 5 worker-pool model)

▸ blocking-read.txtworker-thread model

  ┌── data ready? ─── YES → copy bytes, return n
  │
  └────────────────── NO  → BLOCK this thread until data arrives

Node sets all its TCP sockets to non-blocking. This is the foundational property that makes the whole event-loop model work:

!
Lock this in
Node never lets the main JS thread sit inside a blocking socket syscall. Every socket fd is non-blocking. When there's nothing to do, the kernel returns EAGAIN, and Node uses a separate mechanism — epoll_wait — to find out when there will be something to do.

§ 7 · Readiness APIsHow Node knows when there's something to do

If sockets are non-blocking and we never sleep on them directly, how does Node know when a socket has new data, or when a new connection has been accepted? Answer: the kernel provides a separate API whose entire purpose is "tell me which fds are ready."

On Linux that is epoll. Three syscalls:

  • epoll_create1() — make an epoll instance (itself an fd).
  • epoll_ctl(EPOLL_CTL_ADD, fd, events) — register interest in events on fd.
  • epoll_wait(timeout) — block this thread until at least one registered fd is ready (or the timeout expires).

An epoll instance, drawn

│   └────────────────────────────────────────────────┘      │
└───────────────────────────────────────────────────────────┘

When the main JS thread calls epoll_wait():

  • If the ready list is empty → the thread is parked on the epoll wait queue (BLOCKED state).
  • When the kernel later marks any registered fd as ready (e.g. a packet arrives, the handshake completes, send buffer drains), it wakes any threads on that epoll's wait queue.
  • epoll_wait returns with the list of ready fds.
!
Lock this in
The main JS thread does sleep — but it sleeps inside epoll_wait, waiting on all registered sockets and timers at once, not on any single one. That single sleep is how Node services thousands of connections with one thread.

kqueue (macOS/BSD) and IOCP (Windows) differ in shape — IOCP is a completion API, not a readiness API — but libuv hides the difference. Mentally, on every platform, the model from Node's perspective is "tell me what's ready, on the main thread, in one call."

§ 8 · Why TCP Doesn't Use the Worker PoolThe single most important contrast with Part 5

Side-by-side comparison

▸ fs-vs-tcp.txttwo paths through libuv
┌─────────────────────────────┬──────────────────────────────┬────────────────────────────────┐

│                             │ in read() inside kernel      │ sleeps in epoll_wait           │

│ Readiness API involved?     │ NO                           │ YES (epoll/kqueue/IOCP)        │
│ Completion delivered via    │ eventfd → epoll → main loop  │ epoll directly tells main loop │
│ Main JS thread sleeps in    │ epoll_wait                   │ epoll_wait                     │
│                             │ (waiting on completion fd)   │ (waiting on the sockets)       │
└─────────────────────────────┴──────────────────────────────┴────────────────────────────────┘

Both paths end with the same result: the main JS thread wakes up from epoll_wait, finds out something is ready, runs C++ completion code, calls into V8, and your JS callback / event handler runs. But the cause of the wake-up is different. For files it's "a worker finished and poked the eventfd"; for sockets it's "the kernel saw a packet for fd 18 and marked it ready."

!
Internalize this contrast
Same Node, same libuv, same main JS thread. Filesystem ops use the worker pool because syscalls can block. Socket ops use readiness APIs because the kernel can tell you when they won't block. Don't conflate the two paths.

libuv then makes the fd non-blocking with fcntl(17, F_SETFL, O_NONBLOCK) and sets SO_REUSEADDR.

bind()

▸ bind-syscall.txtkernel side
syscall: bind(17, sockaddr{ family=AF_INET, addr=0.0.0.0, port=3000 })

Kernel:
  - check that 0.0.0.0:3000 is not already bound by another socket
    (without SO_REUSEADDR, that's a hard failure)
  - record local addr/port on the struct sock

If another process already owns port 3000, this is the moment you get EADDRINUSE — which surfaces in JS as the famous Error: listen EADDRINUSE.

  - allocate the SYN queue and accept queue
  - now this socket can receive SYN packets

If the send buffer fills up (slow client, lossy network), the kernel returns EAGAIN for the leftover. libuv stores the unwritten bytes inside the uv_tcp_t and registers interest in EPOLLOUT for fd 18. When the kernel later drains enough of the send buffer to accept more bytes, it marks fd 18 EPOLLOUT-ready, the main thread wakes from epoll_wait, libuv finishes the write, and only then does it call your 'drain' event / completion callback.

§ 24 · Wrong Mental Model vs CorrectSix wrong takes — and what's actually true

Wrong
net.createServer spawns a thread per connection.
It does not. There is one main JS thread. Every connection is a non-blocking fd registered with one shared epoll/kqueue/IOCP, and one thread services them all by reacting to readiness events.
Wrong
TCP I/O uses the libuv worker pool.
It does not. Plain TCP accept/read/write go through libuv's event loop + readiness API. The worker pool is for things the kernel can't do non-blockingly well — filesystem ops, DNS, crypto, compression. Don't conflate the two paths.
Wrong
The 'connection' event fires when a SYN arrives.
It fires after the kernel has fully completed the 3-way handshake and the main JS thread has subsequently woken from epoll_wait, drained the accept queue, allocated a new fd, built a net.Socket, and emitted the event.
Wrong
socket.on('data', cb) means cb fires for every TCP segment.
TCP is a byte stream. Segments are an implementation detail. Node fires 'data' whenever a read() returns some bytes. One 'data' may correspond to many segments coalesced in the recv buffer; one segment may be split across multiple 'data' events. Never assume message framing.
Wrong
The main JS thread spins and polls sockets in a loop.
No. The main JS thread sleeps in epoll_wait. It uses 0% CPU when idle. The kernel wakes it precisely when something is ready. This is the entire reason Node is efficient at high connection counts.
Wrong
socket.write sends bytes to the network.
socket.write copies bytes into the kernel's send buffer for that connection. The kernel decides when to actually transmit them, in what segments, with what timing, and handles retransmits. From your code's perspective, you're filling a buffer, not driving the wire.

Correct mental model

▸ correct-model.txtfive layers
JS world:        starts the server, attaches event handlers, calls write()
Native/libuv:    runs epoll_wait on the main thread, dispatches readiness
                 events, performs non-blocking syscalls, copies bytes into
                 JS Buffers and back
OS kernel:       owns the listening socket, the SYN/accept queues, all
                 connection sockets, all recv/send buffers, all TCP state,
                 all retransmits, the entire 3-way handshake
NIC + driver:    physically transfers bytes; raises interrupts when packets
                 arrive
Main JS thread:  the only thread executing your JS; also the thread that
                 sleeps in epoll_wait; never blocks on any single socket
!
Lock this in
A Node TCP server is, at the OS level, one thread sleeping in epoll_wait. That single sleeping thread, plus the kernel doing all the heavy lifting, is what gives Node its concurrency.

§ 25 · CPU-bound vs I/O-bound — TCP editionNon-blocking doesn't make CPU-bound JS faster

The same warning from Part 5 applies, just sharper:

▸ cpu-bound-timeline.txt5-second sync loop
Time ────────────────────────────────────────────────────►

Main JS thread:
[A connect] [B connect] [BIG SYNC LOOP ......................] [A data] [B data]

Kernel:
[handshake A] [handshake B] [bytes arriving for A ...........]
              [handshake B] [bytes arriving for B ...........]
                            [send buffers backing up ........]

While your handler does a 5-second synchronous computation:

  • new connections still complete in the kernel (handshakes don't need your code)
  • they pile up on the accept queue, which has a limit (the backlog)
  • once that queue fills, the kernel drops or refuses additional SYNs
  • existing connections accumulate bytes in their recv buffers; if those fill, TCP flow control closes the receive window and the peer is told to wait
  • nothing in JS happens until the loop ends

The main JS thread is still single-threaded. The kernel is buffering everything for you, but its buffers are finite.

!
Lock this in
"Non-blocking I/O" doesn't make CPU-bound JS faster. It just means slow networks don't freeze the server. CPU-bound work still blocks every connection, because every connection ultimately funnels through the same main JS thread.

§ 26 · The AnalogyThe reception desk · the phone exchange · the mailroom

If fs.readFile is "customer / cashier / warehouse worker," then net.createServer is something different: nobody walks anywhere. There is one bored receptionist, an enormous switchboard, and a back-office mailroom that handles every envelope the post office delivers — without ever asking the receptionist for permission.

▸ reception-analogy.txtthree actors · click each
Receptionist (Main JS thread)
   └─ sleeps at the desk; one switchboard alarm wakes her

Switchboard (epoll / kqueue / IOCP)
   └─ thousands of phone lines, one alarm light per ready line

Mailroom (Kernel TCP/IP stack + NIC)
   └─ handles every envelope, fills mailboxes, rings the alarm

The trick: the receptionist never walks to the mailroom. The mailroom hands her envelopes through a slot at her desk (the recv buffer). She doesn't have to know which line a letter came in on — the switchboard's alarm light tells her exactly which mailbox has new mail. She processes one letter, glances at the board for any other lit alarms, then goes back to sleep.

That's the entire concurrency model. Worker threads don't appear in this picture at all — there's no "warehouse worker" because there's nothing physical to fetch. The kernel and NIC do all the actual work; the receptionist just reads what's been deposited and writes replies into outgoing mailboxes.

§ 28 · Final "Lock This In" SummaryThe whole story, six ways

!
Lock this in · 1
A net.createServer server is, at the OS level: one listening socket fd, plus N accepted connection fds, all registered with one epoll/kqueue/IOCP instance, all serviced by one main JS thread that sleeps in epoll_wait between events.
!
Lock this in · 2
No libuv worker thread is involved in plain TCP I/O. The contrast with fs.readFile is exact and important: filesystem ops use the worker pool because syscalls can block; socket ops use readiness APIs because the kernel can tell you when they won't block.
!
Lock this in · 3
The kernel completes TCP handshakes by itself. By the time JavaScript hears 'connection', the connection has been ESTABLISHED for some time and is sitting in the accept queue waiting for the main thread to wake from epoll_wait and drain it.
!
Lock this in · 4
'data' events do not correspond to TCP segments. They correspond to "the kernel said fd is readable, so libuv called read() and got these bytes." TCP is a byte stream; framing is your job.
!
Lock this in · 5
socket.write() doesn't transmit. It copies into the kernel send buffer. Backpressure is the moment that buffer is full — write() returns EAGAIN, libuv waits for EPOLLOUT, and Node tells you false so you can pause.
The full invariant
  1. JavaScript creates the server and registers handlers.
  2. The main JS thread issues socket/bind/listen/epoll_ctl syscalls.
  3. The kernel owns all TCP state and completes handshakes alone.
  4. The main JS thread sleeps in epoll_wait until the kernel signals readiness.
  5. libuv drains ready fds with non-blocking syscalls.
  6. V8 emits 'connection' / 'data' / 'end' / 'close' on the main JS thread.

That is the full net.createServer story from your JavaScript through the kernel TCP/IP stack, the NIC, and back up to your event handlers — without ever touching a worker thread.
