01 — Architecture Overview

WHAT DRIVES THE LOOP

Node.js is a single-threaded, non-blocking I/O runtime built on two pillars: V8 (Google's JavaScript engine, handling parsing, compilation via Ignition/TurboFan, and garbage collection) and libuv (a cross-platform async I/O library written in C, providing the event loop, thread pool, and OS abstraction). Between them sits the Node.js binding layer — a set of C++ addons that expose libuv handles and V8 callbacks.

When you write fs.readFile(), Node calls into C++, which calls libuv, which issues an OS syscall (e.g. io_uring_submit on Linux or kqueue on macOS), and parks the request. The JavaScript thread is immediately free. When the OS signals completion, libuv queues a callback, and the event loop picks it up on its next relevant tick.

⬡ JavaScript / V8
V8 Ignition Bytecode

Interprets JS → bytecode. Profiles hot paths for TurboFan JIT compilation. Manages hidden classes, inline caches.

V8 TurboFan JIT

Compiles hot bytecode → optimized machine code using speculative deoptimization. Deopt triggers re-entry to Ignition.

V8 Orinoco GC

Generational, tri-color mark-sweep. New-space (32MB) uses Scavenger. Old-space uses concurrent incremental marking to minimize stop-the-world pauses.

NODE Bindings Layer

C++ code (e.g. node_file.cc) using the V8 C++ API to expose native capabilities. process.binding() is the old path; internalBinding() is the modern one.

⟲ libuv Event Loop Phases

Executed in strict sequential order per iteration ("tick")

01 timers

Executes setTimeout / setInterval callbacks whose threshold has expired. Checks libuv's min-heap of timers. The delay is a minimum, not a guarantee — depends on system load and prior phase duration.

02 pending callbacks

Executes I/O callbacks deferred from the previous iteration — specifically, TCP errors from ECONNREFUSED and similar system-level errors that libuv couldn't report immediately.

03 idle / prepare

Internal libuv housekeeping. uv__run_idle handles are invoked. These run on every loop tick and are used internally by Node.js (e.g. to keep the loop alive). Not directly accessible from JS.

04 poll

The most critical phase. Calls into the OS I/O multiplexer (epoll_wait / kqueue / IOCP). Blocks if no other phases have work, up to a calculated timeout. New I/O callbacks are executed here.

05 check

setImmediate() callbacks fire here. Always runs after poll, even if poll phase was blocked. libuv uses a uv__io_check handle for this. Preferred over setTimeout(fn, 0) for post-I/O scheduling.

06 close callbacks

Fires close events for handles that were closed abruptly — e.g. socket.destroy(). Emits 'close' events on streams and sockets. Final phase before the loop re-evaluates whether to continue.

Why: Sync completes (1, 8). Then microtasks drain: nextTick queue runs first → prints 5, schedules a Promise. Then Promise queue runs: the Promise from line 3 → prints 3, schedules a nextTick. nextTick queue is not empty again — it now has two items. Priority flips back to nextTick: prints 4. Then Promise from inside nextTick: prints 6. All microtasks exhausted. Event loop enters timers phase (setTimeout → 2). Then check phase (setImmediate → 7).

Note: Prior to Node.js 11, nextTick and Promise queues were drained only between phases, not after each individual callback. Node 11+ changed this to match browser behavior.

04 — Phase Deep Dives

PHASE INTERNALS

Each phase of the event loop has specific internal mechanics that affect how and when your callbacks execute. Understanding these at the C-level unlocks the ability to reason about performance pathology.

01
Timers Phase — uv__run_timers()
min-heap, threshold semantics
⌄

libuv stores all pending timers in a min-heap keyed by expiry time (uv_timer_t.timeout in milliseconds since loop start). On each loop iteration, the timers phase calls uv__run_timers(loop), which peeks at the heap root. If loop->time >= timer->timeout, the timer fires and is removed or rescheduled (for intervals).

The critical insight is that loop->time is NOT updated continuously. It is updated once per loop iteration by uv__update_time(loop), which calls uv_hrtime() (a wrapper around clock_gettime(CLOCK_MONOTONIC) on Linux). This means all timers that expire during a single poll phase wakeup will share the same loop->time value, and the timer firing order within a single "batch" depends purely on heap order.

The 1ms drift you've probably observed: Node.js applies a Math.max(1, delay) on timer registration. So setTimeout(fn, 0) becomes setTimeout(fn, 1) internally. If the event loop iteration takes longer than 1ms to start (likely on a loaded system), the timer fires. If it starts within 1ms, it doesn't. This is why setTimeout(fn, 0) vs setImmediate(fn) ordering is non-deterministic outside of I/O callbacks.

ℹ
Timer coalescing: Multiple setTimeout calls with the same delay share the same min-heap node. libuv will fire them all in the same timers phase pass, in insertion order.
deps/uv/src/timer.c (simplified)
// libuv timer heap check — simplified
void uv__run_timers(uv_loop_t* loop) {
  struct heap_node* heap_node;
  uv_timer_t* handle;

  for (;;) {
    heap_node = heap_min(timer_heap(loop));  // O(1) peek
    if (heap_node == NULL) break;

    handle = QUEUE_DATA(heap_node, uv_timer_t, heap_node);
    if (handle->timeout > loop->time) break;  // Not expired yet

    uv_timer_stop(handle);       // O(log n) heap removal
    uv_timer_again(handle);      // Reschedule if interval
    handle->timer_cb(handle);   // Fire callback → back to JS
  }
}
04
Poll Phase — uv__io_poll()
epoll, blocking timeout, wakeup mechanics
⌄

The poll phase is where Node.js actually waits for I/O. It calls uv__io_poll(loop, timeout) where timeout is computed as the minimum time until the next timer expires (or 0 if there are pending callbacks, or -1 to block indefinitely).

On Linux, this translates to epoll_pwait(loop->backend_fd, events, ARRAY_SIZE(events), timeout, sigmask). The kernel will block the thread until: (1) a file descriptor becomes readable/writable/has an error, (2) the timeout expires, or (3) a signal interrupts the syscall. When events arrive, the kernel copies up to ARRAY_SIZE(events) (1024 in libuv) event structs to userspace, and libuv iterates them, invoking the registered callbacks.

On macOS, kevent with a timeout is used. On Windows, GetQueuedCompletionStatusEx pulls from the I/O Completion Port. Despite the platform differences, the semantics are identical: the main thread blocks here and only here.

🚨
Blocking the poll phase: Any synchronous CPU-intensive work in a callback blocks poll from calling back into the kernel. During this time, no I/O events can be processed — this is the source of "blocking the event loop." Profiling with --prof or clinic.js identifies these hot spots.

The poll phase also has a subtle interaction with handle reference counting. libuv maintains a count of "active" and "referenced" handles. The loop exits when there are no more referenced handles with pending I/O and no pending timers. This is why calling timer.unref() lets Node exit even if a timer is pending — it decrements the ref count.

Timeout Calculation (simplified from uv/src/unix/core.c)
static int uv__backend_timeout(uv_loop_t* loop) {
  if (loop->stop_flag != 0) return 0;
  if (!uv__has_active_handles(loop) && !uv__has_active_reqs(loop))
    return 0;  // Loop should exit
  if (!QUEUE_EMPTY(&loop->idle_handles)) return 0;  // Idle handles → don't block
  if (!QUEUE_EMPTY(&loop->pending_queue)) return 0;
  if (loop->closing_handles) return 0;

  return uv__next_timeout(loop);  // ms until next timer, or -1 (block forever)
}
⊕
Thread Pool — libuv work queue
UV_THREADPOOL_SIZE, work/done queue, ENOBUFS
⌄

For operations that cannot be made non-blocking by the OS (like filesystem operations — open(), stat(), read() on local disk, and dns.lookup() which calls getaddrinfo()), libuv dispatches the work to its internal thread pool via uv_queue_work().

The pool has UV_THREADPOOL_SIZE threads (default: 4, max: 1024 via env var). Work items are pushed onto a shared wq (work queue) protected by a mutex. Idle threads wait on a condition variable. When work is submitted, a thread is woken, picks up the work, executes the blocking C call (e.g. pread64()), then pushes the result onto the done queue and writes one byte to the loop's wakeup_fd — an internal pipe that libuv uses to interrupt the poll phase's epoll_wait.

This means every fs.readFile() involves: one async request allocation, one work queue push, one thread wakeup, one blocking syscall on a pool thread, one byte written to the wakeup pipe, one epoll event fired, and one callback scheduled into the poll phase. Understanding this overhead is why using streams instead of readFile for large files is significant.

μ
process.nextTick() — Node.js Internals
nextTickQueue, tickInfo, C++ boundary
⌄

process.nextTick() is not part of the event loop specification. It is implemented in Node.js itself via lib/internal/process/task_queues.js. The queue is drained in node::InternalCallbackScope every time Node transitions from C++ back to JavaScript — which happens at every phase boundary and after every individual callback completes.

Internally, Node maintains a tickInfo object shared between C++ and JS (via a shared ArrayBuffer). The JS side pushes to a linked list (nextTickQueue) and sets tickInfo[kHasTickScheduled] = 1. The C++ side checks this flag at every C++ → JS re-entry point and calls env->tick_callback_function() to drain the queue.

This is why process.nextTick() is described as firing "before" the next event loop phase — it fires at the boundary between the current JS frame returning to C++ and C++ re-entering JS for the next item. Conceptually it's like: current callback finishes → C++ sees kHasTickScheduled → runs all nextTick callbacks → re-checks → if empty, continues to next phase item or phase itself.

lib/internal/process/task_queues.js (simplified)
// Simplified nextTick queue drain
function processTicksAndRejections() {
  let tock;
  do {
    while (tock = queue.shift()) {
        Reflect.apply(tock.callback, tock.domain, tock.args);
        // If callback added more nextTicks, they're in queue now
    }
    // After nextTick queue empty, drain Promise microtasks
    runMicrotasks();  // V8's internal microtask checkpoint
    // If Promise handlers added nextTick, loop again
  } while (!queue.isEmpty() || hasRejections());
}

07 — Mastery Check

TEST YOUR KNOWLEDGE

These questions separate engineers who know Node.js from those who master it.

Q1: You call setTimeout(fn, 0) and setImmediate(fn) from within a net.createServer() connection callback. What is the guaranteed execution order?
✓ Correct. Inside any I/O callback (poll phase), after the callback completes, the loop proceeds to check phase (setImmediate) before cycling back to timers. The setTimeout(fn, 0) timer can only fire in the NEXT loop iteration's timers phase — by which time setImmediate has already executed.
Q2: You have a Promise chain where each .then() schedules another .then(). Meanwhile, a pending setTimeout(fn, 1) should be ready to fire. When does the setTimeout callback execute?
✓ Correct. The microtask queue (Promise callbacks) is drained completely before the event loop can advance to any new phase. A self-replenishing Promise chain starves the timers phase entirely. This is the Promise equivalent of process.nextTick starvation — both microtask queues must be fully empty for the macrotask loop to continue.
Q3: You set UV_THREADPOOL_SIZE=4 (default). You fire 5 concurrent fs.readFile() calls simultaneously. What happens to the 5th call at the OS level?
✓ Correct. libuv's work queue is unbounded (it's a linked list). The 5th request is placed on the queue and will be picked up by the first thread that finishes. No ENOBUFS, no automatic thread spawning. This can cause cascading latency: if threads are busy with slow operations (like bcrypt or slow disk), queue depth grows and all subsequent I/O latency increases proportionally.
Q4: What does process.nextTick() registered inside another process.nextTick() do?
✓ Correct. The nextTick queue is processed in FIFO order, and new entries added during processing are appended to the same queue and drained in the same cycle. The drain loop is: while(nextTickQueue.length) { run one; }. This is why recursive nextTick can starve the event loop — the queue never becomes empty.
Q5: A Node.js process is running a single setInterval(fn, 1000) with no other code. Under what condition does the process NOT exit after the interval fires?
✓ Correct. setInterval is implemented via a uv_timer_t handle that is "active" and "referenced" by default. As long as there is at least one referenced, active handle or request, the loop continues. The process only exits when clearInterval() is called (which calls uv_timer_stop() and decrements active handle count) or when timer.unref() is called to make the handle "unreferenced".
