Architecture deep-dive · Next.js 16 · App Router vs Pages Router

Two routers,
one framework

Next.js ships two complete routing systems. The original pages/ router made React server-rendering easy and ruled from 2016. The newer app/ router, stable since 2023 and the default since v13, rebuilt the foundation on React Server Components — moving the default execution environment from the browser to the server. This is a tour of both architectures: how each one turns a request into a page, what problem each was built to solve, and the specific forces that made Next.js change its mind. 04 — Why Next.js switched

      
Five forces, one rewrite.

      
The App Router wasn't a coat of paint on the old one — it's a different architecture because the old one had hit structural ceilings. These are the forces that pushed the default execution environment from the browser back to the server.

    

    

      

        Force 01
        
        
React itself moved

        
React shipped  as a first-class primitive. A framework built around the old "everything is a client component" model couldn't expose them cleanly. The App Router is the runtime that makes RSC real.

      

      

        Force 02
        
        
Layouts that persist

        
The Pages Router had no real ; the  hack re-ran on every navigation. The App Router makes  a true tree that survives navigation — .

      

      

        Force 03
        
        
Streaming & Suspense

        
Page-level data fetching is all-or-nothing: nothing renders until  resolves. The App Router is built on React 18 , so a static shell ships instantly and slow data fills in via .

      

      

        Force 04
        
        
Kill the waterfall

        
Tying data to the page meant child components fetched on the client, one after another — a . With server-side , each component fetches its own data on the server, in parallel.

      

      

        Force 05
        
        
Less JavaScript shipped

        
In the Pages Router the whole tree hydrates whether it's interactive or not. Server Components ship zero JS, so a content-heavy page can hand the browser almost nothing — the single biggest lever on .

06 — Which should you use?

      
It is not a clean kill.

      
The App Router is the future and the default, but "default" is not "always." The new model trades simplicity for power: the server/client boundary and the caching layers are real cognitive cost. Here is the honest split.

    

    

      

        Reach for App Router
        
Default for anything new

        
    
          
  • You want minimal client JS on content-heavy pages — marketing, docs, commerce, dashboards with a static shell.
    • 
          
  • You need  or per-section  and .
    • 
          
  • You want data and secrets to stay on the server via  and .
    • 
          
  • You're starting fresh and want the features Next.js ships to first.
    • 
        

      

      

        Pages Router still fits
        
Stable, simple, known

        
    
          
  • You have a large, working app where a rewrite buys little — it's in , not removed.
    • 
          
  • Your app is fundamentally a client-side SPA and the server-first model adds friction, not value.
    • 
          
  • You depend on libraries or patterns that haven't fully adapted to the RSC boundary.
    • 
          
  • The team already moves fast in it and the 's learning curve isn't worth paying right now.
    • 
        

      

    

    

      You don't have to choose globally. Both routers run in the same app — app/ and pages/ coexist, so teams routinely migrate  rather than all at once. New surfaces go in app/; the old ones keep working until they're worth moving.
