SECTION 00The central truth

A JavaScript program begins as human-readable text, but the CPU cannot execute text. The CPU only executes machine instructions, which are bytes with specific meanings.

Unlike C, JavaScript has no separate compile step you run by hand. There is no .exe produced ahead of time, no linker you invoke, no object file sitting on disk. The entire JavaScript engine exists to transform this:

JavaScripthuman-readable text
console.log("Hello");

into bytes the CPU understands, at the moment the program runs, in multiple representations, getting faster each time.

That is the central difference from C:

  • C: translation happens once, ahead of time, on the developer's machine.
  • JavaScript: translation happens at runtime, on the user's machine, repeatedly, adaptively.

When you write JavaScript in VS Code, WebStorm, or Cursor, the IDE is mostly a convenience layer. It edits text, highlights syntax, and runs language servers. It does not execute your JavaScript.

SECTION 04Stage -1: V8 starts up

4.1 Isolate

An Isolate is a single instance of V8: one heap, one GC, one set of compiled code, one execution thread.

V8 ISOLATE · nested containers one per Node main thread / Worker

In Node.js, the main thread has one Isolate. Each worker_threads.Worker gets its own. They cannot share JS objects directly — only structured-cloned messages.

In a browser, each renderer process has one Isolate per "process group," shared across same-origin frames.

4.2 Context

A Context is an execution environment with its own global object. Inside one Isolate you can have many Contexts. Each browser iframe is a Context. Node's vm.createContext() creates one. When code in Context A calls into Context B, GC and the heap are shared, but the global objects (window, globalThis) are different.

4.3 The snapshot

Here's where it gets interesting.

V8's built-in objects — Array.prototype.push, Object, Math.sin, JSON.parse, Promise, all of them — are themselves heap objects with hidden classes and machine code. Building all of that from scratch on every startup would take ~100ms.

So V8 builds a snapshot at compile time: a binary blob representing the initial heap state with all the builtins already constructed.

SNAPSHOT LIFECYCLE · click any node build time → runtime

This is why node -e "console.log(1)" starts in ~50ms instead of ~500ms. Most of the work was done at V8 build time.

4.4 Builtins

Array.prototype.push is not interpreted JavaScript. It's a C++ function compiled to machine code, written in V8's internal DSL called Torque (which compiles to a thing called CodeStubAssembler, which lowers to machine code).

When your code does arr.push(x), the engine:

  1. Looks up push on arr.__proto__ (Array.prototype)
  2. Finds a function whose code pointer points into V8's pre-compiled builtin code
  3. Calls it directly — same call instruction it would use for any function

Builtins live in a special read-only memory region inside the Isolate. They're shared across all Contexts in that Isolate.

!
Lock this in
Most "JavaScript" you call is actually pre-compiled C++/Torque, mmapped from a snapshot. Only your code goes through Ignition + JIT.

STEP 1 Build time · init mode

V8 in init mode: building the world from scratch

"Init mode" isn't a configuration toggle — it's a separate small executable called mksnapshot that runs once, when V8 itself is being compiled. Its entire job is to build a complete JavaScript world the slow way, capture the result, and exit.

▾

What "special bootstrapping mode" actually is

When V8 is built (which happens when Node, Chrome, or any embedder is built), the build system produces two binaries: regular V8, and a one-shot tool called mksnapshot. mksnapshot is V8 with a single trick: it's started with the flag --no-snapshot, which tells V8 it must construct everything from primitives instead of loading a pre-built world.

Inside mksnapshot, V8 calls a function in its source called Genesis. Genesis is the only place in the codebase that builds the JavaScript world from scratch. Every other binary skips this entirely.

MKSNAPSHOT · what it does runs once, at V8 build time

What "the initial JavaScript world" contains

The bootstrap creates everything that exists on globalThis before your code runs. Specifically:

A
The Roots — V8 maintains a fixed-size table of pointers to "well-known" objects: true, false, null, undefined, the empty string, the empty FixedArray, every prototype Map. Roots are how the GC and serializer find everything else.
B
The Native Context — Per-Realm storage for Object, Array, Function, Promise, Map, Set, Error and ~30 more constructors. When you write new Array(), V8 looks the constructor up here.
C
Prototype objects — Object.prototype, Array.prototype, Function.prototype, etc. Each with all its method properties already attached.
D
Hidden classes (Maps in V8 terms) — One per shape. The Map for Object.prototype, the Map for an empty plain object, the Map for an empty Array, and so on.
E
Compiled code — Every builtin's machine code (covered in Step 2).

Roughly 20,000–30,000 heap objects in total, all wired together with the right prototype chains and the right Maps.

Why "the slow way" is slow

Imagine doing all of this on every Node startup. The bootstrap is a sequential dance with hard ordering constraints — you can't shortcut it because each step depends on the previous one being already on the heap.

Genesis · simplified pseudocode
// 1. Allocate Object.prototype's Map (the empty Map)
empty_map = Map.create(instance_type=JS_OBJECT, size=0)

// 2. Allocate Object.prototype itself, using that Map
obj_proto = JSObject.alloc(empty_map)

// 3. Add hasOwnProperty, toString, valueOf, isPrototypeOf...
// each addition triggers a Map TRANSITION (new Map)
add_property(obj_proto, "hasOwnProperty", has_own_proto_fn)
add_property(obj_proto, "toString", to_string_fn)
add_property(obj_proto, "valueOf", value_of_fn)
// ... ~10 more properties, ~10 more Map transitions

// 4. NOW we can build Function.prototype, since its [[Prototype]]
// must be Object.prototype which now exists.
fn_proto = JSFunction.alloc(...)
fn_proto.__proto__ = obj_proto

// 5. Now Array.prototype (also requires Object.prototype)
arr_proto = JSArray.prototype.alloc(...)
arr_proto.__proto__ = obj_proto

// ... ~30 more constructors, all with strict ordering

Every add_property call allocates from the heap, computes a string hash, finds or creates a Map transition, and builds a new descriptor entry. Multiply by hundreds of properties across thousands of objects and you get hundreds of milliseconds of work — pure CPU, no I/O, on every startup.

The snapshot is V8's solution: do this once, freeze the result, never repeat it.

!
Lock this in
mksnapshot is the only V8 binary that ever does cold bootstrap. Every other run — including every node invocation — inherits its frozen output. When you start Node, you're not building a JavaScript world. You're loading one.
STEP 2 Build time · compile builtins

Compile builtins: from Torque to machine code

"Compile builtins" means: take the source code of Array.prototype.push, Object.assign, Promise, JSON.parse, and ~thousands of others, and produce real x86-64 (or ARM64) machine code that V8 can call directly. The source isn't C++ — it's a V8-invented DSL called Torque.

▾

What Torque is

Torque is a domain-specific language V8 introduced in 2018 to write builtins safely. It looks like TypeScript with V8-specific types: Smi, HeapObject, JSArray, String, JSAny, etc. The compiler enforces these types, so you can't accidentally pass a Smi where a HeapObject is expected, and you can't forget a write barrier.

Before Torque, builtins were written in CodeStubAssembler (CSA) — a C++ API for emitting machine-code stubs directly. CSA was bug-prone (tag mismatches, missing barriers); Torque compiles down to CSA and adds the type checking automatically. Most builtins migrated to Torque between 2018 and 2022.

The compilation pipeline · step by step

TORQUE COMPILATION · pipeline runs once during V8 build

A real Torque builtin

This is roughly what Array.prototype.indexOf looks like in Torque (simplified):

torque · array.tq
// Real V8 source, slightly trimmed
transitioning javascript builtin
ArrayPrototypeIndexOf(
  js-implicit context: NativeContext, receiver: JSAny)
  (...arguments): JSAny {
  const length: Number = GetLengthProperty(receiver);

  if (length == 0) return -1;

  const searchElement: JSAny =
    arguments[0];

  try {
    // Fast path: dense Smi/Object array
    const array: FastJSArray =
      Cast<FastJSArray>(receiver) otherwise Slow;
    return FastIndexOf(array, length, fromIndex, searchElement);
  } label Slow {
    return GenericIndexOf(receiver, length, fromIndex, searchElement);
  }
}

Notice the typed casts (Cast<FastJSArray>), the otherwise labels for fall-through paths, and the implicit NativeContext parameter. The Torque compiler enforces all of this at compile time.

Why a DSL instead of plain C++?

1
Type safety V8 cares about. Plain C++ types don't distinguish Smi from HeapObject pointer. Torque does. It's impossible to accidentally SmiUntag a HeapObject in Torque source.
2
Automatic write barriers. When you store a pointer into a heap object, V8's incremental GC needs notification. Torque inserts these calls automatically; in CSA you had to remember manually.
3
Better optimization. Because Torque knows types statically, the backend can specialize calling conventions. Smi adds compile to a single add; HeapObject loads compile with the correct tag-clearing.
4
Cross-platform asm output. One .tq file produces x86-64, ARM64, and other architectures' machine code automatically through the TurboFan backend.

By the end of Step 2, every builtin function is sitting in the heap as a Code object — a piece of machine code wrapped in a V8 heap header. Calling Array.prototype.push.call(arr, 1) is a direct jump to that code, no interpretation in between.

!
Lock this in
When you call arr.push(x), you are calling pre-compiled machine code that was produced from typed Torque source during V8's own build. Most of "JavaScript" is not interpreted JavaScript — it's static native code.
STEP 3 Build time · serialize the heap

Serialize the heap: live objects → flat blob

After steps 1 and 2, V8's heap is fully populated — Maps, JSFunctions, Strings, Code objects, the Roots, the Native Context. Serialization walks this graph and writes it out as a single binary blob with every pointer translated into a portable form.

▾

What's in the heap at this point

By the end of bootstrap + builtin compilation, the heap looks roughly like this:

The serialization walk · step by step

1
Start at the Roots. The Roots table is a fixed list (~250 entries) of well-known pointers V8 always knows about: true, false, undefined, every prototype Map, the empty FixedArray. Everything reachable in the JS world is reachable from the Roots.
2
Breadth-first walk. The serializer maintains a queue. For each object pulled out, it: assigns an integer ID, writes the object's type tag (e.g. kJSObject, kCode, kString, kMap), then writes its fields. Pointer fields cause referenced objects to get queued.
3
Pointers become IDs. Inside the blob, an object's pointer to another object isn't a memory address — it's the ID assigned in step 2. A separate pointer table maps each ID to its byte offset in the blob.
4
Absolute pointers go in the relocation table. Some pointers can't be relativized — for example, machine code that contains an embedded address to an external C function. Those get recorded in a relocation table along with where they appear in the blob, so they can be patched at runtime once the actual base address is known.
5
Write a header. Version string, magic bytes, target architecture, total size, builtin count. The header is how V8 confirms the blob matches the binary at load time. Mismatched version → fatal error.
6
Output the file. Everything concatenated → snapshot_blob.bin, typically 1-3 MB.

Why pointer-rewriting is the hard part

A live heap is full of memory addresses. Object A at 0x7f3a:1240 points to object B at 0x7f3a:5680. But the next time you load this heap into a process, those addresses won't be valid — every process gets a different virtual layout.

The serializer's job is to strip away the addresses and replace them with portable references (object IDs, blob offsets, plus the relocation table for pointers that can't be relativized). The result is position-independent: it can be loaded at any address.

!
Lock this in
The blob is V8-version-specific. The exact bit-layout of every heap object can change between V8 versions, so a snapshot from V8 12.4 is unreadable to V8 12.5. This is why node_modules's native bindings sometimes need recompiling — same constraint applies more loosely.
STEP 4 Build time · embed in node binary

Embed in node binary: blob → executable

After step 3 you have a 1-3 MB binary blob sitting on disk: snapshot_blob.bin. Step 4 takes those bytes and links them directly into the final Node executable as static data. When you install Node, the JS world is bundled inside the binary — there is no separate snapshot file to ship.

▾

From blob bytes to executable bytes

EMBEDDING · build pipeline link blob into final node binary

The four sub-stages · in detail

1
Generate a C++ source file from the blob. A small tool (often called blob_to_cc or similar) reads snapshot_blob.bin and writes it as a .cc file containing one giant const uint8_t array. This is the only "magic" — it's just bytes-as-array literal.
2
Compile the C++ to an object file. The compiler (clang/gcc) turns embedded.cc into embedded.o. Because the array is const, it gets placed in the .rodata section — read-only data. The compiler doesn't care that it's a snapshot; to it, it's just a big byte array.
3
Link with the rest of Node. The linker concatenates embedded.o with all the other object files that make up Node (V8's source files, libuv, OpenSSL, etc.). The final result is a single node executable, and the .rodata section now contains the snapshot bytes alongside other read-only data.
4
Reference symbols. The C++ array name (v8_snapshot_blob_data) becomes a linker symbol — V8's runtime code references it by name. At link time, the linker resolves the symbol to point at the embedded bytes. From V8's perspective, accessing the snapshot is just dereferencing a global variable.

Why static linking instead of a separate file?

1
One artifact to ship. No "where is snapshot.bin" path resolution. No risk of mismatched files. Distribute one Node binary and the snapshot is already inside.
2
Free I/O. The OS already maps .rodata when it loads the binary's segments at process start. No additional open() + read() needed.
3
Version safety. A V8 12.4 binary literally cannot load a V8 12.5 snapshot — they're physically inseparable. No version skew possible.
4
ASLR-compatible. The OS can place the binary anywhere in virtual memory; the snapshot moves with it. Combined with the relocation table (Step B), this is how the snapshot tolerates random load addresses.
!

STEP A Runtime · mmap snapshot blob

mmap the snapshot: lazy, zero-copy loading

When you run node, V8 doesn't read() the snapshot bytes into a buffer. It uses mmap — a syscall that maps file (or binary segment) bytes directly into the process's virtual address space. No copying, no allocation. The OS lazily loads pages from disk only when V8 actually touches them.

▾

What mmap does

mmap is a POSIX syscall that establishes a mapping between a region of virtual memory in your process and either a file on disk or anonymous memory. After mmap returns:

A
Your process has a virtual address range that "contains" the file's bytes — but the bytes haven't been read into RAM yet. The kernel just records the mapping in the process's page table.
B
The first time you read a virtual page, the CPU triggers a page fault (because the page isn't physically backed yet). The kernel handles the fault by reading the right disk sector(s) into RAM and updating the page table.
C
Subsequent reads of that page hit RAM — they're as fast as any other memory access.
D
If memory pressure rises, the kernel can evict mapped pages without writing them back (they're clean — the file is the source of truth). Re-reading them just causes another fault and another disk read.

The runtime sequence · what happens when you run node

PROCESS ADDRESS SPACE · pages backed lazily no read() · no malloc · no copy

Why mmap beats read

1
No copy. A read() call copies bytes from the kernel's page cache into a userspace buffer you allocated. mmap doesn't — your virtual address range is the page cache (when faulted).
2
No malloc. No buffer to allocate. mmap just modifies the process page table. Memory accounting shows up as RSS only after you actually touch pages.
3
Lazy. If your code never touches half the snapshot pages (because it doesn't use those builtins), those pages never get loaded. RAM saved.
4
Shared across processes. Two Node processes mapping the same binary share the underlying physical pages of the snapshot. The kernel does this transparently. RAM saved across processes too.
5
Reclaimable. Under memory pressure, mapped pages can be evicted without disk writeback (the file is the source of truth). The system can free RAM aggressively.

STEP B Runtime · fix up pointers

Fix up pointers: relocation in microseconds

The snapshot was serialized at build time, but at runtime it gets mapped into a different virtual address space — courtesy of ASLR, every Node process gets a random base address. Any pointer in the snapshot that referred to an absolute address is now wrong. V8 walks the relocation table and patches them. The whole pass takes microseconds.

▾

Why ASLR breaks raw pointers

Address Space Layout Randomization (ASLR) is a security feature in every modern OS. It deliberately loads each binary at a random virtual address, making memory-corruption exploits harder (the attacker can't predict where things will land).

That means every time you run node, the binary's .rodata section — and the snapshot inside it — lives at a different virtual address. Run twice and you'll see something like:

two runs of the same node binary · different addresses
$ node -e 'console.log(1)'
   .rodata mapped at: 0x55a4_8c12_0000     ; snapshot starts here

$ node -e 'console.log(1)'
   .rodata mapped at: 0x7f23_9b80_3000     ; different address!

$ node -e 'console.log(1)'
   .rodata mapped at: 0x562b_3a45_7000     ; different again

If a pointer inside the snapshot bytes contained the literal value 0x55a4_8c12_8a40 (a build-time guess), it would be valid in run #1 but garbage in runs #2 and #3. Almost all pointers in the snapshot are relative (object IDs resolved through the pointer table — see Step 3), but some can't be:

A
Code embedded references. Compiled machine code (from Step 2) sometimes contains absolute addresses for things like helper function calls or external C function references.
B
Object pointers in code. A compiled builtin might bake the address of a specific Map or String into its instruction stream — e.g., Array.prototype.push may directly reference the Array Map.
C
External references. Pointers from snapshot data to V8 runtime functions (which live in .text, not in the snapshot) need fixup against a side table of known functions.

The relocation table

To handle these, the serializer (Step 3) records every position in the blob where an absolute pointer appears, along with metadata for how to patch it. This is the relocation table. It's a compact list, written into the blob alongside the actual data:

RELOCATION FIXUP · table walks the blob microseconds · just memory writes

The fixup loop · step by step

1
Discover the actual base address. After mmap (Step A), V8 knows where the snapshot region lives in this process's virtual memory. Call this blob_base.
2
Walk the relocation table. The table is a sequence of (offset, kind, target) entries. V8 reads it linearly.
3
For each entry, patch. Compute the absolute address of the patch site: addr = blob_base + entry.offset. Read the existing 8 bytes there. Add blob_base to it (relocating a pointer relative to the snapshot's start). Write back.
4
External references use a side table. For pointers to V8 runtime functions (which live elsewhere in the binary), V8 has an external reference table — an array of pointers to known functions. The relocation entry's target is an index into this table; V8 writes the indexed pointer to the patch site.
5
Done. Every absolute pointer in the snapshot now points to the right place in this process's address space. The JS world is wired up correctly for this run.

Why this is so fast

The whole pass is a tight memory-walking loop — no parsing, no allocation, no I/O. With ~tens of thousands of relocation entries, on modern hardware:

A
Cache-friendly. The relocation table is contiguous; reading it is sequential. The patch sites are within the snapshot region (which mmap just mapped). All in L1/L2 cache after a few iterations.
B
Branch-predictable. The loop body has small fixed paths per relocation kind. Modern CPUs nail the branch prediction.
C
No syscalls. Just userspace memory writes to pages V8 already mapped.

Result: a few hundred microseconds at most. Step B is essentially "free" compared to the milliseconds spent elsewhere in startup.

SECTION 09Stage 4: The interpreter executes bytecode

Ignition is both the bytecode generator and the interpreter that executes it.

9.1 The naive interpreter you might imagine

A textbook interpreter looks like:

C++ · pseudocode
while (true) {
  uint8_t opcode = bytecode[pc];
  switch (opcode) {
    case Ldar: { /* load */                pc += 2; break; }
    case Add:  { /* add */                 pc += 4; break; }
    case Return: { return accumulator; }
    // ~250 cases
  }
}

This works. It is also slow, for one CPU-architecture reason: the central switch is one indirect branch. The CPU's branch predictor only has so much state to predict where a single shared branch goes next. With ~250 possible targets, prediction accuracy collapses, and the CPU stalls on every dispatch.

9.2 V8's threaded interpreter

V8 doesn't write the interpreter as a switch. It writes each opcode handler as a separate piece of machine code (generated by TurboFan at V8 build time), and ends each handler with a tail-call to the next handler.

A handler conceptually compiles to:

x86-64 · asm sketch
; <handler for Ldar>
;   - perform the load
;   - advance the pc
;   - dispatch to next handler

mov  rax, [r12 + rbx*8]      ; load register value into accumulator
                              ; (r12 = bytecode array, rbx = register operand)
add  r9, 2                    ; advance bytecode offset by Ldar's size
movzx rax, byte [r12 + r9]    ; load NEXT opcode byte
jmp  [r15 + rax*8]            ; tail-call into dispatch table[next_opcode]

Now the dispatch is at the end of every handler, not in one central location. The CPU has many distinct branch sites, each with its own prediction state. After Ldar, the most likely next opcode is some specific subset; after Add, a different subset. The branch predictor can learn each site independently.

Result: the threaded interpreter is roughly 2× faster than the naive switch interpreter, with no algorithmic changes.

The interpreter runs JS bytecode using fixed CPU registers on x86-64:

The accumulator is what makes V8's bytecode "register-based with an accumulator." Most ops implicitly read or write rax. This keeps the bytecode small — you don't encode source/dest registers for every op.

9.4 What happens during Ldar a1

Concretely, when V8 executes Ldar a1 from our add example:

step-by-step execution
State:
  r12 = pointer to BytecodeArray bytes [0b 04 3b 03 00 ae]
  r9  = 0  (we're at the start)
  rax = whatever (about to be overwritten)
  rbp points to the frame; arguments are at [rbp+16], [rbp+24], ...

Step 1: opcode dispatch already happened — we're inside Ldar's handler
Step 2: read the operand byte (0x04) at [r12 + r9 + 1]
Step 3: compute the source — for parameter a1, that's [rbp + 24]
Step 4: load: rax ← [rbp + 24]    (this is `b`)
Step 5: r9 += 2                    (Ldar is 2 bytes)
Step 6: load next opcode byte: al ← [r12 + r9]   (which is 0x3b for Add)
Step 7: jump to dispatch_table[0x3b]  → Add's handler

Steps 6 and 7 are the "tail-call to next handler." The CPU never returns to a central loop.

10.4 Smi tagging

The Smi(1) above is not the integer 1 stored as 4 bytes. JavaScript's tagged-pointer scheme distinguishes pointers from small integers in the same word.

V8 on 64-bit (with pointer compression, 32-bit values inside the heap):

SMI TAGGING · 32-bit tagged value low bit = type discriminator

So the integer 1 is stored as bit pattern 0x00000002 (1 << 1). The integer 2 is stored as 0x00000004. A pointer to a heap object is <aligned address> | 1.

This single design decision affects every operation in V8. Every integer add must check that both operands are Smis. Every property read must check that the result isn't a Smi before dereferencing it. We'll see those checks become explicit machine code in section 12.

10.5 Why property order matters

JavaScript

const b = { y: 2, x: 1 };

a and b have different Maps. V8 builds Maps by following a transition tree:

MAP TRANSITION TREE · property order matters {x, y} ≠ {y, x} at the engine level

Code that reads .x from objects with both Maps is polymorphic. Code that reads .x from objects all built {x, y, z} is monomorphic.

This is why React advice "always include all keys, in the same order, every render" matters — it keeps Maps stable.

SECTION 11Stage 6: JIT compilation tiers

Once a function is hot enough, V8 promotes it. There are three JIT tiers above Ignition:

JIT TIER LADDER · click any tier cold ↑ very hot · with deopt back-arrow

11.1 Sparkplug

Sparkplug doesn't even build an IR. It walks bytecode and emits machine code instruction-by-instruction. Each Ldar becomes a mov. Each Add becomes the same logic the threaded interpreter handler would do, but inlined directly with no dispatch.

Compilation takes microseconds. The benefit is removing the ~2-3 ns per opcode that interpreter dispatch costs.

11.2 Maglev

Builds SSA form. Uses feedback to specialize: if the IC says Add always sees Smis, Maglev emits Smi-only code with a deopt fallback. Doesn't do heavy optimization passes (no big inlining, no escape analysis).

Takes milliseconds to compile. Produces code 2-3× faster than Sparkplug.

11.3 TurboFan

Full optimizing compiler. Inlines aggressively. Eliminates redundant type checks. Hoists loads out of loops. Allocates objects on the stack when escape analysis allows. Specializes math operations.

And — speculatively optimizes. We'll see this in actual machine code below.

11.5 Deoptimization

If add("foo", "bar") is called after the function was specialized for Smis:

  1. Hits the test dl, 0x1 check
  2. dl's low bit is 1 (it's a string pointer, a HeapObject)
  3. jnz fires → jumps to deopt site
  4. V8's deoptimizer runs:
    • Reconstructs the interpreter frame from the optimized frame
    • Finds the right bytecode offset to resume at
    • Discards the optimized code
    • Marks the function as "do not re-optimize with Smi assumption"
  5. Execution continues in Ignition
  6. Type feedback updates: now sees [String, String] too
  7. Eventually re-optimizes with both Smi and String specializations, or gives up and falls back to a generic Add

Deopt is expensive (microseconds), but it's an investment — V8 will not make the same mistake twice.

This is part of why JS engine engineering is so complex: there are 3-4 different ABIs in use simultaneously inside one process, and the engine has to bridge them efficiently.

14.4 Live bindings

The "indirect binding" detail matters. Consider:

counter.js
export let count = 0;
export function increment() { count++; }
main.js
import { count, increment } from './counter.js';
console.log(count); // 0
increment();
console.log(count); // 1

In CJS, count would be a copy at require time, and the second log would print 0. In ESM, count is an indirect binding to counter.js's slot. When counter.js mutates its local count, main.js sees the new value because it's the same slot.

15.2 Allocation: the bump allocator

For:

JavaScript
const obj = { x: 1, y: 2 };

Allocation in young gen is just:

bump allocator
free_top = young_gen.top
new_obj  = free_top
young_gen.top += sizeof(JSObject)   ; bump
if (young_gen.top > young_gen.limit)
  trigger_scavenger()

A single increment plus a limit check. Allocating millions of short-lived objects per second is ordinary.

15.3 Scavenger: collecting young gen

The young generation is split in half: from-space and to-space. Allocations only happen in from-space. When from-space fills up:

CHENEY'S ALGORITHM · scavenger GC copy live, free dead

Cost is proportional to live data, not total allocations. Garbage doesn't get touched.

Objects that survive two scavenges get promoted to the old generation (different copy destination, same algorithm during that one cycle).

15.4 The remembered set: tracking old → young pointers

Problem: the scavenger only walks young gen. But what if an old-gen object holds a pointer to a young-gen object? We can't miss that root.

Solution: a remembered set, a side-table of "locations in old gen that point into young gen."

When JS code writes a pointer into an old-gen object's field, the engine inserts a check:

C++ · pseudocode
void WritePointerField(HeapObject* obj, int offset, HeapObject* value) {
  obj->RawWriteField(offset, value);

  if (InOldGen(obj) && InYoungGen(value)) {
    AddToRememberedSet(obj, offset);
  }
}

This write barrier runs on every pointer write. The implementation is heavily optimized — typically a few instructions checking memory page bits — but it's never zero cost.

During scavenger GC, the remembered set is walked as additional roots. We don't have to scan all of old gen. That's the whole reason generational GC works.

15.5 Mark-compact: collecting old gen

Old gen objects tend to live a long time. Copying them all every cycle would be wasteful. So old gen uses mark-compact instead.

MARK-COMPACT · tri-color invariant white → grey → black

15.6 Incremental and concurrent marking

A naive mark phase pauses JS execution for the entire walk. For a 1GB heap that can be hundreds of milliseconds — a janky disaster.

V8 marks incrementally: do a few milliseconds of marking, run JS for a while, mark more. And concurrently: do marking on a background thread.

This sounds simple but introduces a problem: while marking is paused, JS code might mutate the heap. Specifically, JS might:

incremental marking · the danger
1. Read pointer from BLACK object (already marked)
2. Write that pointer into a WHITE object (not yet marked)
3. Remove the pointer from the BLACK object
4. Now the WHITE object is unreachable from anywhere we'll visit
   → GC will incorrectly think it's garbage

This violates the tri-color invariant: a BLACK object now points to a WHITE object.

Solution: another write barrier. Every pointer write during marking:

C++ · pseudocode
void WritePointerField(HeapObject* obj, int offset, HeapObject* value) {
  obj->RawWriteField(offset, value);

  // Generational barrier (as before)
  if (InOldGen(obj) && InYoungGen(value)) {
    AddToRememberedSet(obj, offset);
  }

  // Incremental marking barrier
  if (marking_active && IsBlack(obj) && IsWhite(value)) {
    MakeGrey(value);
    PushToMarkingQueue(value);
  }
}

Now incremental/concurrent marking is safe. JS pays a tiny cost on every pointer write, in exchange for not having multi-hundred-millisecond GC pauses.

!
Lock this in
A JavaScript app that stutters is often hitting GC. GC cost is approximately proportional to allocation rate of long-lived objects + old-gen size. Reducing allocations in hot paths reduces GC pressure directly.

This is the deep reason React advice like "use stable references with useMemo/useCallback" matters. Every fresh closure or array allocated on every render is GC pressure.

15.7 The call stack

When optimized JS calls a function, it uses the native CPU stack with standard call/ret. The stack frame contains:

  • The return address
  • Saved frame pointer (rbp)
  • Saved registers (caller-saved by convention)
  • Local variables that didn't fit in registers
  • A "frame type marker" so the GC knows whether this is a JS frame, an interpreter frame, or a C++ frame

The GC walks frames during collection to find roots. It needs to know which slots in each frame hold tagged pointers (so they can be visited and updated) versus raw values (so they're left alone). For optimized code, V8 stores this metadata as a side-table per code object.

For the interpreter, V8 maintains a parallel "interpreter stack" within the heap. Each bytecode invocation has an InterpreterFrame holding the registers, accumulator, bytecode array pointer, etc. This is what powers the call stack you see in DevTools when you're not optimized.

SECTION 16The event loop

The engine doesn't drive the program. The host environment does.

event loop · pseudocode
while (alive) {
  task = macrotask_queue.pop()
  if (task) execute_to_completion(task)

  while (microtask_queue.not_empty()) {
    mt = microtask_queue.pop()

!
Lock this in
JavaScript is single-threaded for your code. The host does I/O and timers in other threads, then queues callbacks back to the main thread. "Async" doesn't mean "parallel" — it means "deferred to a later turn of the loop."

await is a microtask scheduling mechanism. setTimeout(fn, 0) is a macrotask. They are different queues with different priority — and that's why await continuations run before setTimeout(0) callbacks even though both are "as soon as possible."

SECTION 19What the engine does NOT do

The engine does not:

  • Type-check your code in any language sense (no int x = "hello" rejection)
  • Tell you about logic bugs
  • Care what file your code came from
  • Distinguish TypeScript from JavaScript (TS is gone before the engine sees it)
  • Know about your bundler, your framework, your build chain

The engine does:

  • Parse, interpret, compile, optimize, deoptimize, GC
  • Watch your runtime behavior and adapt
  • Throw runtime errors when operations fail (undefined is not a function)

The host does:

  • Fetch sources (HTTP, fs)
  • Provide APIs (DOM, fetch, fs, setTimeout, console)
  • Drive the event loop
  • Manage threads (web workers, worker_threads)
