The renderer parks it

The function suspends on await; the renderer parks it, resumes when the row returns, and folds the data into the returned elements.

One sentence, four verbs, two of them belonging to JavaScript and two to React. This page takes an async Server Component apart along that seam: what the engine does at await, what the Flight server does with the promise it is handed, what reaches the wire and when, and what a Suspense boundary changes for whoever consumes the result. Every timing and every row in the traces below was captured from the real renderer, not sketched.

Two levels, one promise

The sentence reads as if React pauses a function and later un-pauses it. It does not. The async function suspends itself — that is engine behaviour, defined by the language — and React tracks a task that depends on the promise the function handed back. The two levels touch at exactly one object: the component’s own promise.

  • JavaScript level: calling ArticlePage runs its body until the first await, suspends the execution context, and evaluates to a pending Promise. The continuation runs as a microtask when the awaited promise settles.
  • React level: renderFunctionComponent receives that promise instead of elements, wraps it, and the wrapper throws it out of the serialisation walk; renderModel catches it, creates a task, subscribes ping, and writes a placeholder.
  • Neither level holds the thread. Between the suspension and the resumption the process serves other requests, renders the component’s siblings and retries any other task whose promise settled.

The async function suspends itself. React tracks the unfinished task that depends on it. Everything else on this page is a consequence of keeping those two sentences apart.

React invokes the Server Component

The renderer effectively does const result = ArticlePage(props). Because the function is async, the call does not produce the element tree; it produces a promise, while the body has already started executing.

It reaches await

db.query sends the query and returns a promise that the database has not fulfilled yet. The function cannot continue to its return because article does not exist yet.

What “suspends” means

The execution context of the async function is suspended: it is removed from the call stack, its local bindings stay alive in its environment record, and a reaction on the awaited promise holds the only reference back to it. Control returns to the caller. It does not mean the Node.js thread is frozen — the server continues with other work.

Three requests in flight on one thread: A is parked at its await while B and C are rendered. When the row returns, A resumes. “Suspends” describes the async computation, never the thread.

What “the renderer parks it” means

React’s Flight server meets a component whose result is not available yet. It cannot finish that subtree, so it keeps track of the unfinished work as a task — an entry with a status, a dependency and a row id — and continues with whatever other rendering work it can do. The task is not thrown away; it is waiting for its promise to become readable.

The database promise resolves

Fulfilment queues the continuation. When it runs, await db.query(...) evaluates to the row object, article is bound, and execution resumes at the next line.

Now the element tree is constructed

This is “folds the data into the returned elements”: the JSX expressions read article.title and article.body while the elements are built. The data becomes part of the tree the component returns.

The invariant. The element tree is not created with missing article data and filled in later. The component’s returned tree is constructed after the awaited data is available — one construction, with the values in it.

Four things this makes precise:

  • Detection is by return value. processServerComponentReturnValue sees a thenable and wraps it in a lazy element (createLazyWrapperAroundWakeable). The renderer never inspects the function itself.
  • “Parking” is a catch block. readThenable throws the pending promise; renderModel catches it, calls createTask with the lazy as the model, subscribes ping, and returns "$L1". JSON.stringify then moves on to the next child.
  • The continuation resumes first, then React reacts. On the component’s promise two reactions are registered in order: the status tracker, then ping. Both are microtasks; pingTask only schedules performWork with setImmediate.
  • The retry does not call the component again. retryTask renders the task’s model — the lazy — and readThenable now returns the element tree. emitChunk serialises it as row 1; flushCompletedChunks writes it.

The crucial distinction

The wrong picture is a single frozen line: await, React pauses everything, the database returns, React continues. The right picture is a function that returns control while its promise is pending, and a continuation that runs when the promise fulfils — with React as the consumer of the result.

Client Component versus Server Component

The familiar client pattern renders twice — once without data, once with — and keeps the data in state between the two. The server pattern renders once, after the data, and keeps the data in a local binding of a suspended function.

How the renderer continues

React does not literally pause one JavaScript call and jump into another component’s call stack. On the server the renderer maintains a set of tasks; when one meets an unresolved promise, that task is suspended and the walk that contained it carries on. Start with the tree.

Page() returns three React elements — descriptions, not DOM. The root task serialises that array with JSON.stringify, invoking each component as the walk reaches it. When it reaches ArticlePage, the promise comes back pending and the task below is created.

Now the part the sentence compresses into “continues with whatever other rendering work it can do”. Because the walk is a JSON walk, continuing needs no scheduler: renderModel returned a string, so JSON.stringify visits the next array element. Footer runs in the same synchronous pass, 0.1 ms after the suspension. The walk is sequential — Header, then ArticlePage, then Footer — but it is not blocking, because ArticlePage() returned immediately.

Not every component gets a row. A common picture has Header finishing “and producing a record”, then Footer. In production builds synchronous siblings are serialised inline into the parent’s row; only tasks produce rows, and tasks come from the root and from suspensions. Development builds outline every Server Component so debug information (D rows) can attach to it, which is why a dev trace shows far more rows than a production one.

What the client sees meanwhile — where Suspense comes in

While ArticlePage is parked there may be no browser-visible result at all. React does not invent a placeholder for a component that has none. A Suspense boundary is the only source of a fallback, and it changes nothing at the two levels above — only what a consumer may show before the row arrives.

The boundary is an ordinary element to the Flight server: its type is Symbol.for("react.suspense"), serialised as "$Sreact.suspense" in its own row and referenced from the boundary element, whose children is the placeholder "$L2". The decision is made by whoever renders that element.

The HTML side, from the capture

Fizz consumes the same rows that go to the browser. With a boundary it emits the shell as soon as row 0 is decoded, then patches the content in when row 2 arrives.

Why “$L” and not “$”

The reason a boundary can catch the hole at all is the reference kind Flight wrote into the parent row. A lazy reference lets the parent resolve now and suspends only where it is rendered; a plain reference would block the parent row itself.

In the App Router the boundary usually comes from loading.tsx: Next.js wraps the segment’s page in <Suspense fallback={<Loading/>}> when that file exists. Without it, and without your own Suspense, an async page.tsx behaves like the “with siblings” scenario: the renderer continues, the response waits.

What is unfinished, and when the tree is finalized

Before the database resolves, ArticlePage has not reached its return, so there is no returned tree at all — not a tree with a blank title. After it resolves the function resumes and the result exists.

“Finalized” can mean three different things, and they happen at three different moments.

The response is therefore not “build the entire tree, freeze it, serialise it, send it”. It is a loop.

Work units, precisely

The best mental model is not “one giant element tree with holes that fill”. It is a set of tasks, each owning one row id, each completing when its own dependency resolves.

A task moves through a small state machine. The parked async component moves through it once: created PENDING, retried, completed. The root task suspends in place instead of spawning a child, and a component using use can bounce several times if it reads several promises.

The order of events in one turn

The row returns in a poll-phase callback; everything queued by that callback runs before the loop moves on. The retry is deliberately pushed to the check phase.

  • poll: the driver’s socket read resolves the query promise (in the probe, a timer callback).
  • microtasks: the continuation runs and returns; the component’s promise fulfils; its reactions run in registration order — status tracker, then ping, which calls setImmediate.
  • check: performWork retries the task, emitChunk builds the row, flushCompletedChunks writes it. The probe’s own setImmediate, queued by the continuation, ran 0.3 ms before the row was written.

Flight is not “the element tree serialised once at the end”

The picture to discard first.

The better model: rows are produced as tasks complete, and the stream is the sum of those rows. Synchronous siblings do not produce rows of their own — they are serialised inside the row of the task that rendered them.

The server renderer is doing two things at once: executing components (with their synchronous work, awaits, suspensions and resumptions) and producing rows for whatever has completed.

With the boundary in place, the structure goes out first — Header, Footer, the boundary with its fallback and its placeholder — and the article follows as its own row when its task completes.

Rows, not a tree

Flight is not JSON.stringify(entireReactElementTree). It is a protocol of typed rows and references; the client keeps a table of chunks by id and reconstructs elements as rows arrive.

Three different things

A React element, the server task that renders it, and the wire rows that encode the result are not the same object at any point; the client’s decoded tree is a fourth.

The key invariant. Flight is a streaming protocol for communicating the result of Server Component rendering. The thing being streamed is not the element tree; it is the protocol representation of finished work, emitted row by row as the renderer’s tasks complete.
