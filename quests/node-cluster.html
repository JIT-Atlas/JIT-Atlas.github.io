§ 0 · THE SHORT ANSWER FIRST

Four processes, one port, and a file descriptor in the post

Part 10 gave you a second runtime inside one process. This part gives you a second process — and immediately runs into a problem that has no equivalent at the thread level.

Two processes cannot both bind() port 3000. Part 8 showed exactly why: the second bind returns EADDRINUSE, and it is the kernel refusing, not Node. So how do four worker processes end up serving one port?

JAVASCRIPTTHE FOUR LINES THAT HIDE ALL OF IT
if (cluster.isPrimary) {
  for (let i = 0; i < os.availableParallelism(); i++) cluster.fork();
} else {
  http.createServer(handler).listen(3000);   // four processes, same port
}

Before the answer, the same orientation Part 10 opened with — because the thing that changes here is one level further out. Part 10 added a runtime inside your process; cluster adds whole processes beside it.

JAVASCRIPTTHE SMALLEST CLUSTER, AND WHAT IT PRINTS
const cluster = require("node:cluster");
const http = require("node:http");
const os = require("node:os");

if (cluster.isPrimary) {
  // the primary forks and supervises; it never serves a request
  for (let i = 0; i < os.availableParallelism(); i++) cluster.fork();
  cluster.on("exit", (w) => console.log(`worker ${w.process.pid} died`));
} else {
  // every worker runs THIS branch, in its own process, on the same port
  http.createServer((req, res) => res.end(`served by ${process.pid}\n`))
      .listen(3000);
}
SHELLTHREE REQUESTS TO ONE PORT
$ curl localhost:3000   ->  served by 48213
$ curl localhost:3000   ->  served by 48214
$ curl localhost:3000   ->  served by 48215

Three requests to one port, answered by three different processes. Note the shape: the file runs once per process and the branch decides which role each copy plays — the same pattern as Part 10's isMainThread, one level out. The primary is a supervisor, not a server.

The answer is that they do not each bind it. In the default mode exactly one socket is ever created — by the primary — and the file descriptor for it is sent to the workers over a unix domain socket, using a kernel facility built for precisely this. The listen(3000) in a worker is a polite fiction: it is intercepted and turned into a request for a descriptor the primary already holds.

!Lock this in

An fd is a small integer indexing a per-process table, as Part 5 said. Sending one to another process does not send the number — it makes the kernel install the same underlying open file description in the receiver's table, under whatever number happens to be free there.

The trade is exact and it is the whole reason both features exist. A worker thread shares the process and cannot survive its death. A cluster worker survives anything the others do and shares almost nothing.

§ 2 · HOW A DESCRIPTOR TRAVELS

The kernel installs it; the number is meaningless

The mechanism is a POSIX facility older than Node: a unix domain socket can carry ancillary data of type SCM_RIGHTS, and that payload is a list of file descriptors. The kernel reads it, finds the open file description each number refers to in the sender, and installs a reference to the same description in the receiver.

§ 3 · ROUND-ROBIN VS THE KERNEL

Who decides which worker gets the connection

Once several processes hold one listening socket, something has to decide which of them serves the next connection. Node offers two answers, and they behave differently under load.

Round-robin or SO_REUSEPORT
§3 · the two schedulers
the control is the one where the kernel is not distributing anything

SCHED_RR — the default everywhere except Windows — keeps the accept in the primary. The primary accepts each connection and hands the connected socket to a worker in turn, which gives an even distribution at the cost of a round trip through the primary.

SCHED_NONE gives every worker the listening fd and lets them all call accept(). The kernel picks the winner, which is faster and less even — and on Linux, historically, quite badly uneven.

§ 4 · THE KERNEL DOES THE BALANCING

Several real sockets, one port, hashed by connection

There is a third arrangement that cluster does not use but which underpins a lot of modern deployment: SO_REUSEPORT lets several processes each create their own listening socket on the same port, and asks the kernel to distribute incoming connections between them.

Who holds a socket and who chooses
§4 · three arrangements

SO_REUSEPORT

FOUR separate accept queues, one per process, and the kernel picks by hashing the connection tuple. No primary in the path at all, and each worker has its own backlog to fill.
the difference is where the accept queue lives and who picks
!Lock this in

The count of accept queues is the thing to hold on to. One queue means the workers are competing for the same backlog from Part 8; four queues means one slow worker fills only its own, and the kernel keeps handing it connections anyway because the hash does not know it is busy.

§ 5 · THE BILL FOR ISOLATION

Memory and warmup multiply; the machine does not

Part 10's workers were expensive because each carried a V8 isolate. A cluster worker carries that and a process: its own address space, its own copy of every module, its own JIT state, and its own share of the page cache pressure.

What four workers actually cost
§5 · the bill
the control is the case where more workers make throughput worse

The shape to notice is that throughput does not keep climbing. Up to the core count each worker gets a core and the line is roughly linear; past it, the workers are time-slicing against each other, and every extra one adds memory and context switches while adding no capacity.

Copy-on-write helps less than people expect. The pages are shared after fork(), but V8 writes to almost all of them as it warms up — every inline cache and every JIT-compiled function is a write that unshares a page.

§ 6 · THE REWRITE CLUSTER FORCES

The rule is blunt: with cluster, anything you keep in memory is per worker. State that must be shared belongs outside the process — Redis, the database, or a message the primary relays — and "outside the process" is the price of the isolation you bought.

§ 7 · THE REASON TO USE CLUSTER AT ALL

One crash, one worker, one fork

A worker thread cannot survive a segfault, an OOM or a hard process.exit — it shares the process, so the process goes. A cluster worker can, and that is the strongest argument for paying its costs.

JAVASCRIPTTHE SUPERVISOR IN THREE LINES
cluster.on("exit", (worker, code, signal) => {
  console.error(`worker ${worker.process.pid} died (${signal || code})`);
  cluster.fork();                      // replace it
});

The naive version has a well-known failure: if the crash is deterministic — a bad deploy, a config error — this loop forks a fresh worker to die immediately, forever, at whatever rate the machine allows. Real supervisors add a backoff and a cap, which is a large part of what a process manager gives you over these three lines.

!Lock this in

Restarting is only a strategy if the failure is transient. A crash loop is the same shape as Part 4's starvation: a process at 100% CPU, achieving nothing, with nothing in the logs saying it is stuck.

§ 8 · WHAT THE FD PASSING BUYS YOU

Replace the workers while the socket stays open

Because the listening socket belongs to the primary and not to any worker, workers can be replaced without ever closing it. Connections that arrive mid-reload queue in the accept queue — Part 8's backlog — rather than being refused.
