Reading a file is not
an operation. It is a queue.

The fs module has two shapes worth knowing, and they answer different questions. One is the arc: what actually happens between fs.readFile(path, cb) and your callback, which turns out to be four separate syscalls, a thread that is borrowed and returned four times, and a buffer allocated before a single byte has been read. The other is the surface: 41 operations, three flavours, and a set of edges where the intuitive thing and the correct thing come apart.

The work queue, and four threads

Occupancy is measured, not quoted: each read targets a named pipe, and opening the writing end with O_NONBLOCK fails with ENXIO unless a reader is already blocked in open(2). Every index was probed in its own process, because probing releases the thread it measures.

Nothing in Node survives
schematic
The fsync comparison is measured on a 2 MB write. Page-cache occupancy is not directly observable from a Node process — the bar is the argument being made, not a reading.

Every number on this page was measured on this machine, on v22.22.2, and each figure says which run it came from. Pool occupancy was counted by giving ten reads a named pipe each and asking, with a syscall, which of them held a thread. Descriptor counts come from /proc/self/fd. Timings are medians of twenty runs with the page cache warm, so they compare API paths rather than storage — a cold read is dominated by the device and none of these would be distinguishable.

Two things are deliberately not claimed. The order of syscalls inside readFile is read from Node's own read path rather than traced, because this container has no strace. And this process runs as root, so EACCES never appears in the error catalogue — it is absent rather than invented.

The timeline is the one assembly on the page. Its measured segments are real, but the four steps before the first syscall and the three after the last one are not separately observable from inside a Node process, and are marked as such wherever they appear.
