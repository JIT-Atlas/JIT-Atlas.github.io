01 — The Stack of Abstractions

One Notification, Re-packaged Four Times

Every layer below is the same pattern — notify whoever registered interest — with more policy bolted on. addEventListener is the JS-level expression of the exact thing the kernel does when you register a file descriptor with epoll. Click a layer to open it; press the button to watch a single event travel up.

L0
Hardware · Kernel
An event is a hardware interrupt
keypress → interrupt controller → CPU → kernel ISR

Before any JavaScript exists, an event is electrical. You press a key: the keyboard controller raises a line on the interrupt controller, the CPU stops mid-instruction, and jumps to the kernel's interrupt service routine. The kernel decodes the scancode into something user-space can consume. Same story for the mouse, the NIC signalling a packet, a timer firing.

The kernel doesn't poke every process with every interrupt — that's what the I/O-readiness syscalls are for. The browser blocks in epoll_wait / kqueue / Windows IOCP, or the platform's windowing queue (GetMessage, the Cocoa run loop, Wayland). First principle: an event is just a notification that something happened, and the whole stack re-packages that notification for whoever registered interest.

L1
Host · Browser
The native loop & the JS event loop
run-to-completion · tasks vs microtasks · no preemption

The browser is a native C++ program running its own while(1) blocked on the OS — exactly the event-driven loop you'd write in C. That host loop is not the JS event loop; the JS loop is a much smaller thing running inside it.

JavaScript runs with run-to-completion semantics: once a function starts, nothing interrupts it. No preemption, no timer yanking the CPU mid-statement, no second thread observing a half-mutated object. That's why you never need a mutex around a plain object — and why one while(true) freezes the tab. Two queue tiers sit on top: coarse tasks (one per iteration) and fine microtasks (the whole queue drained after every task). Section 02 runs it live.

L2
DOM · Web Platform
Three-phase dispatch over the DOM tree
capture → target → bubble · composedPath snapshot

A click is delivered to the native loop, the browser hit-tests the layout tree to find the target node, and enqueues a task to dispatch. When the JS loop runs that task, it first snapshots the ancestor chain (composedPath()) — static, so mutating the DOM mid-dispatch can't change the path — then walks it three times: capture (top-down), target, bubble (bottom-up).

The Event object is mutated as it travels: target is fixed, but currentTarget changes per node. Section 03 lets you fire one and watch it. preventDefault() cancels the native default action; stopPropagation() halts the walk; stopImmediatePropagation() also skips remaining listeners on the current node.

L3
React · Synthetic
Delegated, normalized, batched re-simulation
one root listener · SyntheticEvent · fiber-tree walk

React deliberately doesn't use the DOM model directly. onClick is not addEventListener on your button — it's a prop stored in the fiber. React attaches one delegated listener per event type at the root container (the DOM node you mount into, since React 17 — it used to be document). The native event bubbles to the root, React catches it, then runs its own propagation over the fiber tree, wrapping the native event in a SyntheticEvent.

Consequences explored in Sections 05–06: e.stopPropagation() only stops React's synthetic walk; a native handler can starve React's root listener; events carry priorities feeding the concurrent scheduler; and updates inside a handler are batched into one render.

            The trap
            stopPropagation() halts the walk to other nodes but still runs the rest of the listeners on the current node — that's what stopImmediatePropagation() is for. And preventDefault() never stops propagation; it only cancels the browser's default action (navigation, submit, the checkbox toggle above). Conflating the two is the most common dispatch bug.
            

        

    


    
    

        
04 — Where L1 Meets L2

        
Why el.click() Reorders Your Microtasks

        
A microtask checkpoint runs whenever the call stack empties. With a real browser click, the browser invokes each listener, so the stack returns to empty between them — microtasks flush between every listener. But el.click() nests the whole dispatch inside your stack, which never empties until your function returns — so those microtasks all wait until the end. Same listeners, different order, purely from who holds the stack.

05 — React's Synthetic System

        
One Root Listener, A Whole Fiber Walk

        
React attaches one real listener at the root container, not on your elements. The native event bubbles up the DOM to that root; React catches it and re-simulates propagation over the fiber tree as a normalized SyntheticEvent. Run a click — then add a native stopPropagation() mid-tree and watch React's onClick mysteriously never fire.

            Why delegate at all
            Not just "fewer listeners." Handlers change every render (onClick={() => doThing(state)} is a fresh closure each time) — with delegation React just swaps the prop in the fiber, never touching the DOM with add/removeEventListener churn. The 17 move from document to the root was so multiple React versions and micro-frontends can coexist on one page. And onFocus/onBlur actually bind native focusin/focusout, because delegation needs bubbling.
            

        

    


    
    

        
06 — Events Trigger Renders

        
Automatic Batching: Three Updates, One Render

The through-line, bottom to top: a hardware interrupt becomes a kernel notification, becomes a task the browser enqueues, becomes a run-to-completion dispatch walking the capture/target/bubble path, which React intercepts at a single delegated root, re-simulates over its fiber tree as a normalized synthetic event, and uses as the priority-tagged, batched trigger for a render. Each layer is the same "notify the registered party" pattern — just with more policy bolted on.
