§ 0 · THE SHORT ANSWER FIRST

An emitter, a queue of Buffers, and one rule

Two earlier parts were the pieces. Part 2 was the EventEmitter; Part 3 was the Buffer. A stream is what you get when you put a queue of the second inside the first and add a single rule about when to stop filling it.

That rule is backpressure, and it is advisory. write() returns false when the internal queue is above a threshold — and it still accepts your data. Nothing enforces the rule; if you ignore the return value, the queue grows until the process runs out of memory.

JAVASCRIPTTHE WHOLE CONTRACT, IN ONE BRANCH
if (!dest.write(chunk)) {      // false = "the queue is above the threshold"
  src.pause();                 // stop producing
  dest.once("drain", () => src.resume());
}

// write() returned false and STILL took the chunk.
// The only thing false does is tell you.

§ 2 · TWO MODES, THREE APIS, ONE HAZARD

What starts the data moving, and what misses it

A readable stream is either pushing chunks at you or waiting to be asked. Which one it is depends on what you did, and the transition is not always where people think.

And what it costs you
§2 · what puts a stream in flowing mode
the control is attaching the listener late — the data is already gone

The rule underneath is simple: attaching a data listener or calling resume() or pipe() starts the flow, and once it is flowing the stream will not wait for you. Anything emitted before your listener existed was delivered to nobody.

!Lock this in

A readable stream starts in neither mode. The first thing you do to it decides the mode — and if that happens after the source has already begun producing, the chunks in between are simply lost.

§ 3 · AND THE THREE THINGS IT DOES NOT DO

A threshold that changes a return value

highWaterMark gets treated as a memory limit. It is not one, and the difference matters most exactly when you are hoping it is.

§ 4 · WHAT THE BRANCH IS WORTH

A fast producer and a slow consumer

Part 9 measures backpressure for one HTTP response. This is the general case, and the shape is the same whenever the thing producing data is faster than the thing consuming it — which is nearly always, because producing is usually memory and consuming is usually a socket or a disk.

The same 200MB, three ways
§4 · honouring the return value
the control ignores the return value — and the whole payload ends up in memory

Note what does not differ: every mode moves the same bytes and finishes in a comparable time. The only thing that changes is how much of the payload is resident in your process while it happens.

!Lock this in

Backpressure does not make the transfer faster. It keeps the transfer from being paid for in memory — which is the cost that takes a process down rather than merely slowing it.

The symptom is memory that tracks payload size rather than concurrency, and it appears only when the consumer is slow — a client on a bad connection, a disk under load, a downstream service applying its own backpressure. Which means it appears in production and not in staging.

If your memory graph has the shape of your data rather than the shape of your traffic, this is the first thing to look for.

§ 6 · THE DIFFERENCE IS WHAT HAPPENS ON FAILURE

One of them leaks

pipe() handles backpressure for you, which is most of why it exists. What it does not handle is failure — and the consequence is a resource leak that no error message mentions.

What is left behind
§6 · when something fails mid-transfer
the control is pipe with an error — the source is still open and still reading

This is why stream.pipeline exists and why it should be the default. It destroys every stream in the chain when any of them fails, and it gives you one callback — or one promise — for the whole thing rather than an error handler per stream.

!Lock this in

pipe forwards data and nothing else. On failure it leaves the other end open, and a leaked file descriptor from Part 0 is exactly what that looks like a thousand requests later.

§ 7 · THE SAME MACHINERY, COUNTING DIFFERENTLY

When a chunk is not bytes

A stream in object mode carries arbitrary JavaScript values instead of Buffers. Everything in this part still applies; only the units change.

Sixteen of anything
§7 · the same rule, a different unit

64KB of bytes before write() says stop
object mode · highWaterMark 16
objobjobjobjobj… 16 of themeach one 10MB?

The contract is identical and the unit is not. Object mode is a much cheaper way to exhaust memory, because the threshold counts things rather than bytes.
