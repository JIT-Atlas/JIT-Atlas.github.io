§ 0 · The Short Answer FirstThe thread we actually care about

This is the foundational lesson. Everything that comes later in the series — TCP, HTTP, Express, WebSockets, streams, timers, microtasks, crypto, child processes, worker threads — assumes the mental model built here.

We are going to trace this single line:

JavaScript the line we trace 
const fs = require("fs");

fs.readFile("file.txt", (err, data) => {
  console.log(data);
});

…all the way from your JavaScript text down to the CPU and the storage device, and all the way back up to your callback. Along the way, we build the entire CPU → OS → process → thread → syscall → libuv → V8 picture from first principles.

When people say:

"Node.js must not block the thread"

they almost always mean:

the main JavaScript execution thread — the OS thread inside the Node process where V8 runs your JavaScript call stack.

For fs.readFile("file.txt", cb):

  • The main JS thread initiates the work.
  • A worker libuv worker thread (a separate OS thread) actually performs the blocking filesystem syscalls.
  • The kernel OS kernel owns the file, file descriptors, page cache, and storage device.
  • When the read finishes, a completion is queued.
  • The event loop picks it up and the main JS thread runs your callback.
!
Lock this in
fs.readFile does not magically eliminate blocking. It moves the blocking off the main JS thread and onto a libuv worker thread.

The CPU understands things like:

  • LOAD a value from memory into a register
  • ADD / SUB / MUL on registers
  • COMPARE two values
  • JUMP to another address
  • CALL / RETURN
  • syscall instructions (SYSCALL, INT 0x80, SVC, depending on architecture)

The CPU does not understand:

  • JavaScript
  • promises
  • callbacks
  • Express
  • files
  • sockets
  • HTTP
  • fs.readFile

Those are abstractions built on top of raw instructions.

!
Lock this in
The CPU does not understand "JavaScript callbacks." It only executes machine instructions on whichever thread the OS scheduler hands it.

§ 4 · The CPU is Synchronous by DefaultOne instruction at a time

A thread is, at first approximation, "a sequence of instructions executing over time."

▸ thread-timeline.txtlinear execution
Time ─────────────────────────────────────────────►

Thread:  [Instr 1] → [Instr 2] → [Instr 3] → [Instr 4] → ...

Each instruction starts, finishes, and only then does the next one start. There is no built-in "do this in the background" at the CPU level — that has to be engineered above.

This is exactly why "blocking" is dangerous: if a single instruction path can't continue (because it's waiting on disk, network, etc.), the thread stops progressing — even though the CPU itself is fine.

§ 10 · What is a Syscall?Trapping into kernel mode

A syscall is the mechanism by which user-space code asks the kernel to do something privileged. From C, you write:

C

At the CPU level this becomes a special instruction (syscall on x86_64 Linux) that traps into kernel mode.

§ 11 · Why Can a Syscall Block?External reality has latency

Some syscalls finish immediately. getpid() just returns a number the kernel already knows.

Others depend on external reality:

  • disk read
  • network packet
  • terminal input
  • another process

For those, the kernel has two choices:

  1. Return immediately with "not ready, try later" (non-blocking mode).
  2. Put the calling thread to sleep until the data is available (blocking mode).

fs.readFile ultimately ends up in blocking filesystem syscalls under the hood. Here is what blocking looks like:

Lock this in
"Blocking" does not mean the CPU freezes. It means this specific thread is removed from the run queue until the kernel wakes it up. Other threads keep running. Other processes keep running. The CPU is fine.

§ 12 · Which Thread Gets Blocked?Only the one that called the syscall

The thread that made the syscall. Only that one.

▸ which-thread.txtper-thread blocking
Thread A: read(fd, buf, n)   ← blocks Thread A only
Thread B: still running
Thread C: still running

This is the whole reason libuv has a worker thread pool. If Node's main JS thread made a blocking read() directly, the entire JavaScript world would freeze. Instead, Node hands the work to a worker thread, which can safely block without anyone in JS noticing.

§ 13 · Why Is That Bad for Node?The wrong-design version

Imagine a hypothetical Node where fs.readFile blocks the main JS thread:

JavaScripthypothetical · do not do this

  const data = blockingReadFile("big.txt");  // blocks main JS thread
  res.end(data);

✗ Wrong

While the main thread sleeps, no JS runs at all. Not your handler, not timers, not other request handlers, not promise continuations. The server is effectively dead until the read finishes.

Node's entire concurrency story depends on the main JS thread never sitting and waiting for slow OS work. That is the problem libuv solves.

§ 14 · The Problem libuv Solves, Stated PreciselyConstraints & solution

Constraints:

  • JavaScript runs on a single main JS thread (a hard V8/Node design choice).
  • That thread must remain responsive — it has to keep handling requests, timers, callbacks.
  • Many useful operations (disk I/O, DNS, TLS handshakes, crypto, compression) take time.

Solution:

A cross-platform layer (libuv) that:

  • exposes an event loop
  • exposes a worker thread pool for blocking operations
  • wraps OS readiness/completion APIs (epoll on Linux, kqueue on macOS/BSD, IOCP on Windows) for sockets
  • queues completions so the main JS thread can pick them up at safe points

The pieces involved

│ libuv                                                       │

│  │ Event loop (on main thread)│  │ Worker thread pool    │  │

For fs.readFile, the path is worker pool, not epoll. Filesystem I/O on POSIX systems doesn't have a great non-blocking story, so libuv just throws the work onto a worker thread and lets it block there.

For sockets, libuv uses readiness APIs instead. We will hit that in Parts 4, 8 and 9.

§ 17 · Step 2 — Node's JS Wrapper (lib/fs.js)Validation & request allocation

fs.readFile is implemented in JavaScript first. The wrapper:

  • validates the path argument (string, Buffer, or URL)
  • validates the callback (must be a function)
  • normalizes options (encoding, flag, signal, etc.)
  • allocates an internal request object
  • calls down into the native binding

§ 18 · Step 3 — Crossing into Native CodeThe JS↔C++ bridge

JavaScript cannot directly issue OS syscalls. There is no JS instruction kernel.read(fd, buf, n). So Node provides a bridge: C++ bindings registered with V8 as native functions callable from JS.

▸ js-cpp-bridge.txtthree-layer descent
┌──────────────────────────────┐
│ JavaScript world (V8)        │
│   safe, GC'd, high-level     │
└──────────────┬───────────────┘
               │  V8 native function bridge
               ▼
┌──────────────────────────────┐
│ Node C++ internals           │
│   can call C/C++ libraries   │
│   can call libuv             │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ libuv → OS kernel            │
└──────────────────────────────┘

When the JS wrapper calls binding.open(path, flags, mode, req):

  1. V8 sees that binding.open is a registered native function.
  2. V8 marshals the JS arguments into C++ values.
  3. V8 enters the registered C++ function.
  4. The C++ function runs on the main JS thread (still — we haven't gone async yet).
!
Lock this in
Crossing the JS↔C++ boundary does not switch threads. It just switches what kind of code is running on the same OS thread.

§ 27 · Step 11 — Worker reports completion

The worker finishes (open → stat → read → close). It writes the result into the uv_fs_t:

  • success: bytes are in a libuv-allocated buffer; result field = number of bytes
  • failure: result is negative; errno-style error code is set (e.g. UV_ENOENT, UV_EACCES)

It then signals the event loop. On Linux this typically uses an eventfd or self-pipe that epoll_wait is watching. When the main thread is sleeping in epoll_wait, that signal wakes it up.

§ 29 · Step 13 — The callback cannot interrupt running JS

This is the single most-important property of Node's concurrency model.

JavaScript

console.log("done");

Even if the worker finishes the read in 2ms, the callback cannot fire while the loop is running. JavaScript executes run-to-completion.

§ 34 · Wrong mental model vs correct mental model

✗ Wrong
"fs.readFile is non-blocking, so the disk read doesn't block anything."
The disk read absolutely blocks something — it blocks a libuv worker thread in read() inside the kernel. "Non-blocking" in Node-speak means "non-blocking with respect to the main JS thread," not "non-blocking with respect to the kernel."
✗ Wrong
"The callback fires as soon as the file is read."
It fires as soon as (a) the file is read and (b) the JS call stack is empty and (c) the event loop reaches the relevant phase. If you have a giant synchronous loop running, the callback waits.
✗ Wrong
"JavaScript is single-threaded means Node has one thread."
Node has many threads. JavaScript runs on one of them — the main JS thread. Worker threads, V8 GC helpers, and libuv pool threads all coexist in the same process.
✗ Wrong
"libuv runs my callback."
libuv runs the C++ completion routine (AfterRead). That routine, on the main JS thread, eventually asks V8 to invoke your JS callback.
✗ Wrong
"If I await fs.promises.readFile, it's somehow different at the OS level."
It is not. fs.promises.readFile is a thin wrapper that calls the same C++ binding and submits the same uv_fs_t to the same worker pool. The only difference is the JS-level shape of the result (Promise vs callback).

✓ Correct mental model

▸ correct-mental.txt5 layers
JS world:        starts the work, gets the result later via callback/promise
Native/libuv:    moves blocking work off the main JS thread, queues completion
OS kernel:       owns files, fds, page cache, scheduler; can block worker threads
Hardware:        actually moves bytes
Main JS thread:  the thread that must remain free; only it can run your JS

§ 38 · Final "Lock This In" Summary

!
Lock this in
The thread we care about is the main JS thread — the OS thread inside the Node process where V8 runs your call stack.
!
Lock this in
What fs.readFile does: main JS thread sets up the work; a libuv worker thread performs the blocking filesystem syscalls; the main JS thread later runs your callback.
!
Lock this in
What "blocking" means: the OS removes a thread from the run queue until the operation can continue. For fs.readFile, the thread that gets blocked is a worker thread, not the main JS thread.
!
Lock this in
Why the callback runs later: it can only run when (a) the file work is done, (b) completion is queued, (c) the main JS call stack is empty, and (d) the event loop reaches the relevant phase.
The full invariant
  1. JavaScript initiates async work.
  2. Node's C++ bindings + libuv perform or monitor the slow work.
  3. The OS kernel manages the real resources and may block worker threads.
  4. Completions are queued for the main thread.
  5. V8 runs your callback on the main JS thread when it's safe.

That is the full fs.readFile() story from the CPU through the OS, libuv, the worker pool, and back to your callback.
