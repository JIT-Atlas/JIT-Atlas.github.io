Byte custody  /  Node.js

A map of who is holding the data, at every layer, at every instant

Where are my bytes right now?

Every layer of a Node program has something it calls a buffer, and they are not the same thing — some of them store your bytes, some only point at them, and one of them holds nothing at all while appearing to do the most work.

This page answers one question in one way: pick a moment in the journey, and it tells you which layer physically holds the data, who owns that memory, and whether what you are looking at is a copy, a window, or an address.

00 The short answer

Three rules that decide every case

The confusion is not really about buffers. It is about ownership. Once you know which side of an ownership boundary a piece of memory sits on, everything else — whether it copies, whether two things can see the same bytes, whether freeing one frees the other — follows from that.

  • Crossing an ownership boundary copies. Kernel memory and your process's memory are separate address spaces with a syscall between them. Bytes cannot be shared across that line, only transferred. Inbound that happens once; outbound it happens once.
  • Inside your process, nothing copies unless you ask for it. The parser, the readable queue and the chunk your callback receives are all looking at one block of memory. They are windows at different offsets, not successive copies.
  • libuv stores none of your bytes. On the way in it fills memory that Node handed it. On the way out it holds a list of addresses pointing into memory JavaScript still owns. It has queues; it does not have a byte store.
The count, for the path you have selected: bytes come to rest in 4 places on the way in and 5 on the way out, and exactly 2 of those transitions are copies.

Two rows above are the ones that get merged in most people's heads. The read block is memory the operating system filled; a stream's queue is a JavaScript array of chunks. The queue does not contain bytes — it contains objects that point into blocks. One block can be pointed at by several queued chunks at once, and it stays alive as long as any of them does.

03 Copy, window, address

The three kinds of holding, and why only one of them costs memory

“Where are my bytes” is ambiguous because there are three quite different ways a layer can be holding something, and only one of them means the bytes are actually there.

KindWhat existsCostsWhere it happens
copyA second set of the same bytes in different memoryThe full length, twice over, until one is releasedOnly at an ownership boundary, or when you ask for it
windowAn object recording an offset and a length into memory that already existsA few dozen bytes for the object, whatever the lengthEverywhere inside your process
addressA note of where the bytes are, held by a layer that will read them laterNothing — but the target must stay alive until it is doneThe native write queue

The consequence people get bitten by

Because a chunk in your callback is a window and not a copy, the block underneath it stays alive for exactly as long as you keep that chunk. A small window can pin a large block.

04 Inbound moves. Outbound duplicates.

Why the answer to “where is it” is sometimes one place and sometimes two

The two syscall crossings look symmetrical and are not. This is the single fact that makes the question answerable, because it tells you when the bytes are in one place and when they are in several at once.

  • Reading is a move. Once the kernel has copied the socket's queued bytes into your block, it drops its own copy immediately — that space is what the peer is allowed to send more into. Just after the read there is exactly one copy, and it is yours.
  • Writing is a duplicate. When you hand bytes to the kernel, it copies them into the send queue and keeps them, because the peer may not acknowledge and the bytes may need sending again. Your copy and the kernel's copy now both exist, and yours is released on your schedule, not the network's.
  • So a stalled write is expensive twice. The kernel's send queue is full of unacknowledged bytes, and your queue is full of the ones it wouldn't take — two lots of memory for one lot of data.

05 Three kinds of full

One word, backpressure, naming three mechanisms with completely different teeth

Every layer that queues has a notion of being too full, and they are not the same notion. Knowing which one you are looking at tells you whether something will stop you, slow you, or quietly let you run out of memory.

  • Enforced, at the far end. The receiving kernel advertises how much room its receive queue has. When that reaches zero the sending kernel stops transmitting. Nothing in either application gets a say; this is the only limit in the whole stack that physically halts the producer.
  • Opportunistic, in the middle. The native side offers bytes to the kernel and the kernel takes what fits. Whatever it refuses stays queued as addresses and is retried when the socket reports it can accept more. Nothing is dropped, nothing is capped — the queue simply grows.
  • Advisory, at the top. A writable stream compares its queue against a threshold and returns false when it is over. It still accepts the chunk. Nothing enforces the threshold; ignoring the answer costs you memory, not correctness.
This is why the two ends behave so differently when your code stalls. Stop reading and the pressure reaches an enforced limit within one round trip — the sender is physically stopped and your memory stays flat. Ignore a write returning false and the pressure has nowhere to go but your own heap, because everything above the kernel accepts whatever it is given.

06 What the request and response objects really are

Neither one is what its base class suggests

The request object is a readable stream that nothing ever pulls from. A normal readable asks its source for more when it runs low. This one doesn't: the HTTP parser pushes into it as bytes are parsed, and its queue is a place things are put, not a place things are fetched from. Its only real control is being able to say “stop asking the socket for more” when it is over its threshold.

The more surprising half is where the parser sits. On an HTTP connection the parser is attached below the socket's own stream machinery, so incoming bytes go from the read straight into parsing. The socket's readable queue is not in the path at all — it exists, it is empty, and reading from it is not how the request body reaches you.

The response object is two queues, not one

The response is not a plain writable stream either. It sits above the socket and keeps a pending list of its own, because it has work to do that the socket knows nothing about: turning the status line and headers into bytes, deciding chunked framing, and grouping small writes so they leave as one segment rather than several.

  • Your string is encoded here. Passing a string rather than bytes means an encode step, which is a copy — a deliberate one, and unavoidable, since only bytes go on the wire.
  • Its pending list is a separate place bytes can sit from the socket's writable queue. Both can be non-empty at once, and they are counted separately.
  • Ending the response is not the same as the bytes leaving. It means no more application data is coming. Everything below still has to drain.

07 What libuv actually keeps

08 How to see each layer

Turning the model into something you can check at three in the morning

Every layer that holds anything can be observed, and the numbers disagree with each other in useful ways. If your process memory is climbing, the layer whose number is climbing with it is the one holding your data.

The pair worth internalising: a JS queue growing while the native and kernel numbers stay near zero means the bottleneck is you, not the network. The native and kernel numbers pinned high means the peer or the link is the bottleneck and your queue is the symptom. They call for opposite fixes.
