01 The one idea everything hangs on

A byte has no meaning. You impose one.

Every API in this stack is a consequence of a single split: storage versus interpretation. An ArrayBuffer owns a contiguous block of octets and nothing else — it can't even be read directly. Everything you do to those bytes happens through a view: a TypedArray, a DataView, or Node's Buffer. None of them own bytes; they read and write someone else's.

That's the whole curriculum in one line. The byte 0x41 is the letter "A", the number 65, or a quarter of some float — the bits never move, only the lens does. Hold this distinction and every method's existence becomes obvious.

the recurring pattern the same raw bytes  →  choose a lens (type · endianness · encoding)  →  get a value. Change the lens, change the value. The bytes never moved. 
storage    ArrayBuffer        owns the octets, opaque, no accessors
lens · 1   Uint8Array(buf)    → array of bytes (native endian)
lens · 2   DataView(buf)      → any type, any offset, explicit endian
lens · 3   Buffer.from(buf)   → Uint8Array subclass + encodings + I/O

02 Eight bits, two interpretations

Inside one byte — and why −1 is all ones.

Before any view, there is the byte: eight bits, each a power of two. Read those bits as unsigned and the range is 0–255. Read the very same bits as signed (two's complement) and the top bit flips meaning — it now subtracts 128. That's why 0xFF is 255 through one lens and −1 through another. Click the bits.

two's complement, by hand −1 in 8 bits is 1111 1111: take +1 = 0000 0001, invert to 1111 1110, add one → 1111 1111. Set every bit above and watch the signed lens read −1 while the unsigned lens reads 255. Same storage; the sign is a choice.

06 Same bytes, different number

Endianness is just another lens — and a silent one.

Reading a multi-byte integer requires knowing the byte order. DataView forces you to state it; readUInt32LE/BE name it; a plain Uint32Array quietly uses the platform's. Networks and many file formats are big-endian, so guessing wrong gives a plausible-looking, totally wrong number. Flip the switch.

07 Where small Buffers actually live

The Buffer pool — and why allocUnsafe is a footgun.

Node carves small buffers out of a shared ~8 KiB ArrayBuffer as slabs, so each isn't a separate allocation. The consequences: a small Buffer's byteOffset is rarely zero, its .buffer is bigger than the Buffer itself, and allocUnsafe hands you whatever stale bytes were there before. Click a box.

09 The fix · stateful decoding

Emit complete characters, keep the tail.

node:string_decoder exists for exactly this. decoder.write(chunk) returns only the characters it can complete and retains any incomplete trailing bytes internally until the next call. readable.setEncoding('utf8') wires one into the stream for you. Each card opens the same deep-dive the trace nodes do.

const { StringDecoder } = require('node:string_decoder');
const d = new StringDecoder('utf8');
d.write(chunk1); // → "café "  (retains the dangling E2)
d.write(chunk2); // → "€99"    (prepends E2, completes E2 82 AC)
d.end();         // → ""       (nothing buffered, clean)
