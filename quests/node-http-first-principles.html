04 req & res as Streams

The hardest concept.
The most important one.

Why Streams?

When your browser sends data, it doesn't arrive all at once. It arrives in chunks over time:

TCP chunks arriving over time
[t=0ms]
POST /api HTTP/1.1\r\n
[t=5ms]
Host: example.com\r\n
[t=10ms]
\r\n
[t=15ms]
{"userId":
[t=20ms]
123}
⚠ Why This Matters
If Node buffered all of this into memory before giving it to you, large file uploads would crash the server. Streams give you chunks as they arrive — you process and discard.

What req Is

req (IncomingMessage) is a with HTTP metadata attached:

TypeScript
// Stream interface (you listen to events)
req.on('data', chunk => { /* handle chunk — called 1 to 1000 times */ })
req.on('end', () => { /* all chunks received */ })

// HTTP metadata (you read these properties)
req.method      // 'GET', 'POST', etc.
req.url         // '/api/users?id=5'
req.headers     // { 'content-type': 'application/json', ... }
req.httpVersion // '1.1'

Why both? Because HTTP headers are metadata (static), but the body is data (streaming).

What res Is

res (ServerResponse) is a that enforces HTTP ordering:

TypeScript
// Must set status/headers BEFORE writing body
res.statusCode = 200;
res.setHeader('Content-Type', 'application/json');

// THEN write body
res.write('{"success": true}');

// THEN end — forgetting this hangs the browser FOREVER
res.end();
⚠ Strict Ordering
HTTP headers go on the wire first, then the body. Once you call write(), headers are "locked in" — you can't change them. Once you call end(), nothing else can be sent on that connection.
✓ Do This
const chunks: Buffer[] = [];
req.on('data', c => chunks.push(c));
req.on('end', () => {
  const body = Buffer.concat(chunks)
    .toString('utf8');
  const json = JSON.parse(body);
});
✗ Not This
// req.body doesn't exist
// on raw Node http module
const data = req.body;

// Don't assume all data
// has arrived yet
res.end(req.body);

06 Connection Reuse

TCP connections are
expensive. Agent fixes that.

Opening a TCP connection requires a . Plus for HTTPS. This takes 50–200ms — per request — if you don't reuse connections.

✗ Without Agent (Old Way)
Request 1: Open socket → GET / → Close socket
Request 2: Open socket → GET / → Close socket
Request 3: Open socket → GET / → Close socket
→ 3 TCP handshakes = 3× latency
✓ With Agent (Modern)
Request 1: Open socket → GET / → Keep alive
Request 2: Reuse socket → GET / → Keep alive
Request 3: Reuse socket → GET / → Keep alive
→ 1 TCP handshake = 10–100× faster
💡 Why Second Requests Feel Faster
http.globalAgent handles this automatically. It keeps a pool of sockets to remote servers and reuses them. This is why your fetch() to the same server is faster on the second call.

⚠ Server Receives TWO HTTP Requests
The server received OPTIONS /products (asking for permission) AND POST /products (the actual request). Both must be handled. Most frameworks do this automatically with CORS middleware.

CORS Happens in the Browser — Not Node

TypeScript
// Node server never sees a CORS problem
// The browser blocks the response before your code runs

// Browser-side:
fetch(url)
  .then(r => r.json())        // ← Blocked by browser if CORS fails
  .catch(e => console.log(e)) // NetworkError — not a real error

// Node never gets involved in CORS checking
💡 Preflight Is Deterministic
Given cross-origin + POST/PUT/DELETE + application/json Content-Type + any custom headers → preflight always happens. It's not a bug, not a config mistake. It's the browser doing its job.
09 Express Decoration Layer

Express doesn't mutate req.
It decorates it.

Raw Node vs Express

Raw Node http
// Node gives you just a string
req.url === "/products?page=2&cat=vit"

// You must parse manually
const url = new URL(req.url,
  `http://${req.headers.host}`);
const page = url.searchParams.get('page');
Express
// Express parses it for you
console.log(req.query);
// { category: "vitamins", page: "2" }

// Route params: /users/:id
console.log(req.params);
// { id: "123" }

// Body (with middleware)
console.log(req.body);
// { search: "immune support" }

How Express Decorates req

Express doesn't "mutate" the Node request. It adds properties:

TypeScript Types
// Original Node request
type NodeReq = {
  method?: string;
  url?: string;
  headers: Record<string, string | string[] | undefined>;
};

// Express decoration
type ExpressReq = NodeReq & {
  query: Record<string, unknown>;     // Parsed query string
  params: Record<string, string>;     // Route params: /users/:id
  body?: unknown;                       // Parsed body (with middleware)
};
⚠ req.query values are always strings
req.query.page === "2" — always a string, never a number. req.query.active === "true" — always a string, never a boolean. You must parse explicitly with parseInt(), parseFloat(), or === 'true'.
10 Critical Insights

Lock these in.
They come up in interviews.

Insight 01

fetch() is Not "Just an HTTP Call"

It's a browser algorithm that validates input, performs CORS preflight (a separate HTTP request), validates CORS response headers, streams the body, and returns a Promise. All before your .then().

Insight 02

Query Params Are Always Strings

From browser → Node → Express: req.query.page === "2". Always a string. Express never auto-converts types. parseInt() is your responsibility.

Insight 03

Node's req Is Not "The Request"

It's a parsed, stream-backed JavaScript representation of an HTTP message. Raw bytes → llhttp parser → IncomingMessage. The body is still a stream — never buffered by default.

Insight 04

Streaming Is the Default

Both request and response bodies are streams at every layer. Never assume the full body is in memory. Without streams: 1GB upload = 1GB in memory = server crash.

Insight 05

Headers Are Normalized, Not Changed

Browser sends "Accept: application/json" → Node receives req.headers["accept"] === "application/json". Header names are lowercased by Node, values are exact.

Insight 06

CORS Happens in the Browser

Node server never sees a CORS problem. The browser blocks the response before your JS runs. CORS middleware on the server sets the headers that tell the browser it's okay.

Insight 07

res.end() Is Not Optional

If you forget to call res.end(), the browser waits forever. No timeout. No error. Just a pending request that will eventually time out on the client side.

13 Raw Node — Zero Abstraction

req.url is a string.
Everything else is your problem.

Node's http module gives you exactly what the HTTP parser extracted: a raw URL string. It doesn't know about routes. It doesn't parse query params. It doesn't buffer the body.

TypeScript — Raw Node http
import http from 'node:http';

http.createServer((req: http.IncomingMessage, res: http.ServerResponse) => {

  // ① req.url is exactly what came off the wire — never parsed
  //    "/products/42/reviews?page=2&limit=10&sort=rating&filter%5Bmin%5D=4"
  const rawUrl = req.url ?? '/';

  // ② You must construct a full URL to parse it (URL needs an origin)
  const url = new URL(rawUrl, `http://${req.headers.host}`);

  // ③ URLSearchParams: get() returns string | null — never a number
  const page  = Number(url.searchParams.get('page')  ?? '1');   // → 2
  const limit = Number(url.searchParams.get('limit') ?? '20');  // → 10
  const sort  = url.searchParams.get('sort') ?? 'created_at';   // → "rating"

  // ④ filter[min]=4 → key is literally "filter[min]", not a nested object
  const filterMin = url.searchParams.get('filter[min]');       // → "4"

  // ⑤ Route params: Node has NO router — you match manually
  const match = url.pathname.match(/^\/products\/(\d+)\/reviews$/);
  if (!match) { res.statusCode = 404; res.end(); return; }
  const productId = Number(match[1]); // → 42

  // ⑥ Body: always a stream — buffer it yourself
  const chunks: Buffer[] = [];
  req.on('data', c => chunks.push(c));
  req.on('end', () => {
    const body = chunks.length
      ? JSON.parse(Buffer.concat(chunks).toString())
      : null;

    res.setHeader('Content-Type', 'application/json');
    res.end(JSON.stringify({ productId, page, limit, sort, filterMin }));
  });

}).listen(3000);
①
Raw string from the parser — may include URL-encoded chars like %5B for [
②
new URL() needs a base. Use req.headers.host. Will throw if host header is missing.
③
URLSearchParams.get() always returns string | null. You coerce to numbers yourself.
④
Bracket notation stays as a literal key. No nested object. Express's qs parser handles this differently.
⑤
Node has zero routing. You match the URL yourself with regex and extract capture groups.
⑥
Body arrives in chunks. Buffer them all, concat, then parse. No shortcuts.

14 Express — The Classic

Same request. Three lines.
But you need to know what happens under them.

TypeScript — Express v4
import express from 'express';
const app = express();

// ① body-parser middleware — express.json() buffers + parses the stream
//    Must come BEFORE your routes. Attaches parsed body to req.body.
app.use(express.json());

// ② Route definition — uses path-to-regexp under the hood
//    :productId becomes a named capture group in a regex
app.get('/products/:productId/reviews', (req, res) => {

  // ③ Route param — extracted by path-to-regexp, always a string
  const productId = Number(req.params.productId);  // → 42

  // ④ req.query — parsed by Express's query parser (qs by default)
  //    qs handles bracket notation: filter[min]=4 → { filter: { min: "4" } }
  const page  = Number(req.query.page)  || 1;    // req.query.page === "2"
  const limit = Number(req.query.limit) || 20;   // req.query.limit === "10"
  const sort  = req.query.sort as string;        // req.query.sort === "rating"

  // ⑤ Nested bracket notation — qs parses this into a real object
  const filter = req.query.filter as { min?: string };
  // filter.min === "4"  (still a string — qs doesn't coerce types)

  // ⑥ req.body — only exists because express.json() middleware ran
  //    Without that middleware: req.body === undefined
  const body = req.body;

  res.json({ productId, page, limit, sort, filter, body });
});

app.listen(3000);
①
express.json() wraps the raw Node stream. It buffers chunks, detects Content-Type: application/json, parses, and sets req.body.
②
path-to-regexp converts :productId into /^\/products\/(?:([^\/]+?))\//i. Match groups become req.params.
③
req.params.productId is always a string. Even though it looks like a number in the URL. You cast it.
④
req.query is Express's addition — not from Node. All values are strings. qs adds bracket/dot notation support over vanilla URLSearchParams.
⑤
qs parses filter[min]=4 into a nested object { filter: { min: "4" } }. Node's native URLSearchParams treats the entire key literally.
⑥
req.body only exists if middleware ran first. Without express.json(), req.body is undefined — a very common source of bugs.

Express's qs Parser vs URLSearchParams

Express's default query parser is qs, which adds features beyond the Web standard:

qs vs URLSearchParams — Same Query String
// Query string: ?color=red&color=blue&filter[min]=4&filter[max]=10&a.b=1

// ── URLSearchParams (Node / browser native) ──────────────────────────
url.searchParams.get('color')      // → "red"  (first only)
url.searchParams.getAll('color')  // → ["red", "blue"]
url.searchParams.get('filter[min]') // → "4"  (literal key)
url.searchParams.get('a.b')        // → "1"  (literal key)

// ── Express req.query with qs ─────────────────────────────────────────
req.query.color         // → ["red", "blue"]  (auto-array!)
req.query.filter        // → { min: "4", max: "10" }  (nested object)
req.query.a             // → { b: "1" }  (dot notation → nested)

// ── Switching Express to use simple parser (no qs) ───────────────────
app.set('query parser', 'simple'); // uses Node's querystring module
app.set('query parser', 'extended'); // default — uses qs
⚠ The qs Trap
With qs, ?color=red gives you a string but ?color=red&color=blue gives you an string[]. The type of req.query.color changes based on how many values are sent. TypeScript types this as string | ParsedQs | string[] | ParsedQs[] — you must always guard.

15 Hono — Edge-first

TypeScript-native. Built on
web standard APIs. Runs anywhere.

Hono is built on the Fetch API, not on Node's IncomingMessage/ServerResponse directly. Its request object wraps a standard Request, which means it runs identically on Node, Bun, Deno, Cloudflare Workers, and any edge runtime.

TypeScript — Hono v4
import { Hono } from 'hono';

// ① Hono is generic over your env type — full inference chain
const app = new Hono();

// ② Route registration — trie-based router, much faster than regex chains
app.get('/products/:productId/reviews', async (c) => {

  // ③ Route param — c.req.param() returns string, always
  const productId = Number(c.req.param('productId'));  // → 42

  // ④ c.req.query() — uses URLSearchParams internally (Web standard)
  //    No qs, no bracket object nesting — spec-compliant behavior
  const page  = Number(c.req.query('page'))  || 1;   // "2" → 2
  const limit = Number(c.req.query('limit')) || 20;  // "10" → 10
  const sort  = c.req.query('sort') ?? 'created_at'; // "rating"

  // ⑤ filter[min]=4 — literal key, not a nested object (URLSearchParams)
  const filterMin = c.req.query('filter[min]');     // → "4"

  // ⑥ All queries at once — returns Record<string, string>
  const allQuery = c.req.queries();  // { page:"2", limit:"10", ... }

  // ⑦ Body — built-in, no middleware needed. Awaitable. Type-safe with validator.
  const body = await c.req.json();      // reads + parses body stream
  const text = await c.req.text();      // raw string
  const form = await c.req.formData(); // FormData

  // ⑧ Response — c.json() returns a Web standard Response object
  return c.json({ productId, page, limit, sort, filterMin });
});

export default app; // Works as a Cloudflare Worker as-is
①
Hono's generic parameter enables full type inference for variables, bindings, and env — no manual type casting needed with validators.
②
Hono uses a RadixTree/Trie router internally. Faster than Express's sequential regex chain — O(log n) vs O(n) for route matching.
③
Same story as Express — always a string. You coerce manually. The difference is the ergonomics: c.req.param('id') vs req.params.id.
④
c.req.query() calls new URL(req.url).searchParams.get(key) internally. Web standard — no qs, no surprises.
⑤
Unlike Express with qs, Hono doesn't parse bracket notation into nested objects. Spec-compliant: the key is literal.
⑥
c.req.queries() returns all params as a flat Record<string, string>. For multi-value: c.req.queries('color') → string[].
⑦
Body parsing is built-in, async, and uses the Web Fetch API. No middleware registration needed. req.json() is idiomatic.
⑧
Returns a Web standard Response object. Handlers are async and return responses — no side-effect res.end().

Hono with Zod Validation — The Modern Pattern

TypeScript — Hono + @hono/zod-validator
import { Hono } from 'hono';
import { zValidator } from '@hono/zod-validator';
import { z } from 'zod';

const app = new Hono();

const reviewsQuery = z.object({
  page:  z.coerce.number().min(1).default(1),   // "2" → 2 (coerced!)
  limit: z.coerce.number().max(100).default(20),
  sort:  z.enum(['rating', 'created_at', 'helpful']).default('created_at'),
});

app.get(
  '/products/:productId/reviews',
  zValidator('query', reviewsQuery),  // middleware: validates + coerces
  (c) => {
    const { page, limit, sort } = c.req.valid('query');
    // page is number ← TypeScript KNOWS this. No cast needed.
    // limit is number
    // sort is "rating" | "created_at" | "helpful"

    return c.json({ page, limit, sort });
  }
);
💡 Why This Pattern Matters
z.coerce.number() solves the "query params are always strings" problem at the schema layer. By the time you reach your handler, page is already a number and TypeScript knows it. This is the pattern you'd recommend in a senior code review.

The One Pattern to Standardise On

Regardless of framework, this pattern eliminates the entire class of "query param is a string" bugs:

TypeScript — Framework-agnostic Zod coercion pattern
import { z } from 'zod';

// Define your expected shape once
const QuerySchema = z.object({
  page:   z.coerce.number().int().positive().default(1),
  limit:  z.coerce.number().int().min(1).max(100).default(20),
  sort:   z.enum(['rating', 'created_at', 'helpful']).default('created_at'),
  active: z.enum(['true', 'false']).transform(v => v === 'true').default('true'),
});

// Works with any source of string key-value pairs
function parseQuery(raw: Record<string, unknown>) {
  return QuerySchema.parse(raw); // throws ZodError on invalid input
}

// Express
const query = parseQuery(req.query);

// Hono (without zValidator middleware)
const query = parseQuery(c.req.query());

// Raw Node
const raw: Record<string, string> = {};
url.searchParams.forEach((v, k) => { raw[k] = v; });
const query = parseQuery(raw);

// Result: { page: 2, limit: 10, sort: "rating", active: true }
//  Types: { page: number, limit: number, sort: string, active: boolean }
🎓 Senior-Level Takeaway
The framework doesn't solve the "strings problem" — Zod (or another schema library) does. Express's qs gives you nested objects at the cost of non-standard behavior. Hono's URLSearchParams gives you spec compliance but flat strings. The correct answer in any codebase is: validate and coerce at the boundary with a schema.
