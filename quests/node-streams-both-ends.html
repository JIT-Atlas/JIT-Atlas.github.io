"The stream is richer than that iterator" is precisely this: the iterator protocol has exactly two verbs, next() and (optionally) return(). "async, pull-oriented side of a stream"

Two things are being compressed here, and separating them prevents a contradiction later on.

  • Which side. Readable is the readable end — the side a consumer takes bytes out of. Its opposite number is Writable, the end you put bytes into. That framing is exact.
  • Pull versus push. This is not a property of the class. A Readable supports both, and which one you get depends on how you consume it: attach a 'data' handler and the stream pushes at you; call read() or iterate it and you pull. The same object, two modes.

Calling the class "the pull side" collides with the push/pull section further down this page, where 'data' is correctly identified as push. The stable statement is: Readable is the consumer-facing end of a stream, and it exposes both a push interface and a pull interface over one buffer.

for await, token by token

  • for await — legal only inside an async function or a module top level, because it needs somewhere to suspend to.
  • of — makes this an iteration over a sequence protocol, not over an object's keys. The engine calls a method on readable rather than reading its properties.
  • const chunk — a fresh binding created per iteration, in a new declarative environment record for each pass of the loop body.
  • [Symbol.asyncIterator] — the method the engine looks up first. If it is absent, the engine falls back to [Symbol.iterator] and wraps it. A Readable has the async one, so the fallback never fires here.

One step the concise desugaring leaves out: if the loop body throws, or you break, or you return, the engine calls iterator.return() on the way out. On a Readable that call destroys the stream. This is why breaking out of a for await over an HTTP request mid-body leaves the request destroyed rather than merely un-iterated — a behaviour with no equivalent in the on('data') version.

Why the split is guaranteed, not merely possible

"Maybe it arrives" understates it. TCP offers a byte stream with no message boundaries. There is no framing in the protocol that would let the kernel hand your process a complete HTTP body as a unit, and several independent mechanisms actively chop it up:

  • Path MTU. A segment carries roughly 1460 bytes of payload on a standard Ethernet path. A 10 MB body is thousands of segments before it ever reaches the receiver.
  • Kernel receive buffer. Bytes accumulate in the socket's receive queue. Your process gets whatever has arrived at the instant it calls recv() — a partial segment, several segments coalesced, anything.
  • Congestion and flow control. The sender's window opens and closes over the life of the transfer, so arrival is bursty by design.
  • The HTTP parser. Even a single recv() may contain the tail of the headers plus the head of the body, so what reaches the stream is a slice of a slice.

The consequence for your code: a chunk boundary carries no meaning. A multi-byte UTF-8 character can be split across two chunks; a JSON document certainly can. Any code that calls chunk.toString() per chunk and concatenates the strings is already broken for non-ASCII input, and the bug only shows up under a particular chunking.

There is less machinery here than the name suggests

An EventEmitter is a map from event name to a function or an array of functions, plus a loop. Stripped to essentials:

on(name, fn) {
  (this._events[name] ??= []).push(fn);
  return this;
}

emit(name, ...args) {
  const list = this._events[name];
  if (!list) return false;
  for (const fn of [...list]) fn.apply(this, args);
  return true;
}

Four properties follow directly from that loop, and all four surprise people:

  • emit is fully synchronous. It is a for loop. By the time emit returns, every listener has already run to completion. Nothing is queued, and there is no event loop involvement at all.
  • The list is copied before iterating. A listener that removes itself, or adds another, does not disturb the pass in progress.
  • Order is registration order. No priorities.
  • A throw from any listener propagates out of emit and skips the remaining listeners.

The one event with special semantics

'error' is not an ordinary name. If an 'error' event is emitted and there is no listener for it, EventEmitter throws the error object, which on an unhandled path takes down the process. Every other event with no listeners is a silent no-op. On a request this matters: a client that disconnects mid-upload produces an error on the request, and the handler you did not attach is the difference between a logged warning and a crash.

The step that makes the 'data' event possible at all

A Readable does not emit 'data' just because data arrived. It emits 'data' only while readableFlowing === true, and a brand-new stream starts at null. The transition is caused by you:

  1. You call req.on('data', fn).
  2. Inside on, Readable special-cases the name 'data' and calls resume().
  3. resume() sets flowing = true and schedules the actual drain on process.nextTick — not immediately.
  4. From then on, each chunk that reaches the stream is emitted rather than buffered.

What "the stream machinery knows" is, concretely

It is a saved function reference. When read() comes back empty, the iterator stores the promise's own resolve in a field on itself and returns the pending promise. Nothing else happens — no timer, no polling, no loop.

The chain that eventually fires it is entirely event-driven, and each link is code that already exists for other reasons:

  1. The event loop is blocked in the OS event-polling mechanism (epoll_wait on Linux) with the socket's descriptor in the watch set.
  2. Bytes land in the kernel receive queue; the descriptor becomes readable; the poll call returns.
  3. libuv invokes the read callback, which calls recv() and hands the bytes to the HTTP parser.
  4. The parser calls push() on the request, which appends to the buffer and — because a consumer is waiting — emits 'readable'.
  5. The iterator's 'readable' handler retries read(), gets a chunk, and calls the stored resolve.
  6. Resolving schedules the continuation of your async function as a microtask. It runs after the current synchronous work finishes, before the loop moves on.

The suspended async function, throughout, is not on the call stack. Its execution context was captured when it hit await, so the stack was free to unwind all the way back to the event loop. That is precisely what makes "JavaScript continues" true.

Even the already-buffered case yields

When read() succeeds immediately, next() returns an already-resolved promise. await still suspends — it always queues a microtask before resuming. So the loop body never runs synchronously with the next() call, in either case. This is worth knowing because it means a for await loop always gives the microtask queue a turn between chunks, whereas a tight on('data') handler does not.

  • true — the queue is still under the watermark. Carry on.
  • false — the queue is at or over the watermark. The chunk was still accepted and queued. You are being asked to stop, not told that you failed.

Nothing enforces the request. Write a hundred more chunks after a false and all hundred are accepted, queued, and held in the JavaScript heap until the resource can take them. The watermark is a threshold Node consults to decide whether to set needDrain; it is not a cap and it does not reject.

Contrast the read side, where the equivalent lapse is cheap. If a consumer stops reading, chunks accumulate to the watermark and then Node simply stops asking the socket for more — the excess stays in the kernel and then on the network, held there by TCP. On the write side there is no equivalent authority. An ignored false is unbounded memory growth in your process.

'drain' fires on empty, not on "below the mark"

The natural assumption is that 'drain' fires as soon as the queue drops back under the watermark. It does not. Node emits it when the queue reaches zero, and only if a previous write had returned false:

if (state.length === 0 && state.needDrain) {
  state.needDrain = false;
  stream.emit('drain');
}

Two consequences. A stream that is being written to continuously may never emit 'drain', because the queue never quite empties. And 'drain' is not emitted at all unless a write previously returned false — waiting for one you were never promised is a common way to hang a program.

Backpressure on the write path, link by link

On the read side, backpressure was a chain of things that stop happening and it was enforced by TCP several layers below JavaScript. Here the chain runs the other way, and the last link is in your heap rather than on the network.

The important distinction

A Readable gives the consumer a choice of two interfaces and lets the consumer set the pace. A Writable gives the producer one interface and asks the producer to set the pace on its behalf.

Both times the pace is set on the left. On the read side that is the same place as the consumer, so a loop that waits naturally does the right thing. On the write side it is the producer, and nothing in the language makes the producer wait.

Building a tiny Writable from scratch

The read side was easiest to see by writing a minimal async iterator. The write side is easiest to see by writing a minimal write. The whole mechanism is a queue, a flag, and one rule about when the next _write may start.

1. The rule that shapes everything

An implementer's _write is asynchronous — it hands bytes to a socket, a file descriptor, a database — so it takes a callback. The rule Node enforces is:

Only one _write may be in flight at a time, and they run in the order the writes were accepted.

Ordering is not an optimisation Node happens to provide. It is the guarantee that makes a stream a stream rather than a bag of concurrent sends.

2. A minimal implementation

class TinyWritable {
  constructor(hwm = 65536) {
    this.queue = [];
    this.length = 0;
    this.hwm = hwm;
    this.writing = false;
    this.needDrain = false;
    this.ending = false;
  }

  write(chunk) {
    if (this.ending) throw new Error('write after end');
    this.queue.push(chunk);            // always accepted
    this.length += chunk.length;
    this._maybeWrite();
    const ok = this.length < this.hwm;   // measured AFTER accepting
    if (!ok) this.needDrain = true;
    return ok;                          // advice, not a verdict
  }

  _maybeWrite() {
    if (this.writing || this.queue.length === 0) return;
    const chunk = this.queue.shift();
    this.writing = true;

    this._write(chunk, () => {          // implementer calls back
      this.writing = false;
      this.length -= chunk.length;

      if (this.length === 0 && this.needDrain) {
        this.needDrain = false;
        this.emit('drain');            // empty, not merely below hwm
      }
      if (this.queue.length) this._maybeWrite();
      else if (this.ending) this._finish();
    });
  }

  end(chunk) {
    if (chunk !== undefined) this.write(chunk);
    this.ending = true;
    if (!this.writing && this.queue.length === 0) this._finish();
  }

  _finish() {
    this._final(() => this.emit('finish'));
  }
}

Roughly sixty lines, and every behaviour discussed on this page is visible in them. Node's real implementation adds encodings, object mode, cork, _writev batching, error propagation and destroy semantics, but the skeleton is this.

The four lines that matter, at the position they sit in

  • this.queue.push(chunk) before computing the return value — the chunk is committed first. There is no branch in which write declines.
  • const ok = this.length < this.hwm measured after the push. So the write that takes you over the line is the one that returns false, and it has already been accepted. The signal is always one chunk late by construction.
  • if (!ok) this.needDrain = true — this is what arms 'drain'. Without a false return there is nothing to arm it, and the event will never fire.
  • this.writing = true around the _write call — the ordering guarantee, in one flag. Remove it and chunks race.

3. The two production interfaces

With that machinery in place, there are exactly two ways to drive it.

Manual

function writeAll(dest, chunks, done) {
  next();
  function next() {
    while (chunks.length) {
      if (!dest.write(chunks.shift())) {
        dest.once('drain', next);   // stop and wait
        return;
      }
    }
    dest.end(done);
  }
}

The shape is always the same: a loop that can suspend itself, re-entered by an event. It is the callback-era equivalent of an await.

Delegated

import { pipeline } from "node:stream/promises";

await pipeline(source, dest);

Same loop, written once, in the standard library.

Both honour backpressure. They differ entirely on the failure paths, which is where streams actually go wrong.

1. Nothing has been sent yet

On the first line of the handler the response exists but has produced no output at all. No status line, no headers, no body. Compare that with the request, whose metadata was complete before the handler was entered.

The two objects are at opposite ends of their lifecycles at the same instant. That is the cleanest statement of what a request/response pair is.

2. The first write decides the framing

When the first body byte is written, Node has to serialise a status line and headers ahead of it, and to do that it must decide how the body will be delimited.

The example sets no Content-Length, because a file stream does not announce its size to the response. So Node chooses chunked framing, and each write that reaches the socket is wrapped:

The hexadecimal length prefix and the terminating zero-length chunk are added by OutgoingMessage, not by you and not by the socket.

Where the header lock actually happens

The lock is not a timer or a phase — it is a side effect of the first call that produces output. Any of these trip it:

  • res.write(chunk) — headers are serialised and prepended to that first chunk
  • res.end() — even with no body, a complete response must be sent
  • res.writeHead(...) — marks them ready, though the bytes may still be buffered
  • res.flushHeaders() — sends them deliberately, ahead of any body

After any of those, res.headersSent is true and mutating a header throws. The practical consequence for the example above: once pipeline has moved a single chunk, you can no longer change the status code. A read error on the file at that point cannot be turned into a 500 — the client has already been told 200. All you can do is destroy the response, which surfaces at the client as a truncated body rather than an error status.

That asymmetry is worth designing around. If you need the option of failing cleanly, open the file and stat it before writing anything, so the failure happens while the headers are still mutable.

Where this bites in practice

  • Metrics and tracing wrappers that measure queue depth by reaching into _writableState. They work in tests against a PassThrough and throw in production against a response.
  • Libraries that branch on stream type to decide between piping and buffering. A response takes the buffering path, and the backpressure benefit is lost without any error to notice.
  • Type definitions. TypeScript models ServerResponse as extending OutgoingMessage, which is declared as a Writable for practical reasons. So the compiler will happily let you reach for members that do not exist at runtime — the type system agrees with the duck typing, not with instanceof.
