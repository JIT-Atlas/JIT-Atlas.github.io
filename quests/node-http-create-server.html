§ 0 · The Short Answer FirstOne thread, sleeping in epoll_wait — with an HTTP parser bolted on

A Node HTTP server does not use the libuv worker pool to wait for network requests. Network I/O in Node uses an entirely different mechanism: the OS readiness / completion API.

const server = http.createServer((req, res) => {

server.listen(3000);

fs.readFile() uses the libuv worker pool because filesystem syscalls can block. A Node HTTP server uses the OS readiness API (epoll / kqueue / IOCP) because the kernel already knows how to multiplex thousands of sockets without blocking — it can simply tell you when a socket has bytes ready.

The main JS thread never sits and waits on a socket. The OS does the waiting.

§ 1 · The Core ProblemTwo processes, two memories, one wire

A browser is on one machine. A Node server is on another machine (or the same machine via loopback). These two processes do not share memory. They do not share file descriptors. They do not share threads.

They communicate only by sending bytes through a network. So the problem decomposes into nine sub-problems:

  1. How do bytes leave the browser?
  2. How do bytes traverse the OS network stack?
  3. How do bytes arrive at the server's OS?
  4. How does Node know bytes have arrived?
  5. How are HTTP-formatted bytes parsed into req/res objects?
  6. How does Node invoke your JS handler?
  7. How does your JS write a response?
  8. How do those response bytes go back to the browser?
  9. How does the browser interpret them?

Every layer adds a transformation.

§ 3 · Start From CPU RealityThe CPU never understood "the internet"

The CPU does not understand HTTP, TCP, IP, sockets, request handlers, or req and res objects. The CPU only executes machine instructions.

§ 7 · Listening Socket vs Connection SocketOne parent · many children

This is one of the most misunderstood ideas in network programming. A server has two kinds of sockets:

The listening socket

  • one socket
  • bound to a port (e.g. 3000)
  • in LISTEN state
  • does NOT carry data
  • accepts incoming connections

The connection sockets

  • one PER active client connection
  • bound to (server IP : 3000) on local side
  • bound to (client IP : random port) on remote side
  • in ESTABLISHED state
  • carries data for that ONE client

§ 9 · The Browser SideFrom URL to bytes on the wire

We will not deeply trace the browser's internals (Node is the focus), but we need a clear mental model. When the browser hits http://localhost:3000/:

  1. Browser parses URL
  2. Browser checks connection pool — any open conn to localhost:3000?
  3. If not, browser performs DNS lookup — "localhost" → 127.0.0.1
  4. Browser asks kernel for a TCP socket
  5. Browser kernel performs TCP three-way handshake with server
  6. Browser formats HTTP request bytes
  7. Browser writes bytes into kernel's send buffer
  8. Kernel transmits bytes

§ 14 · The OS Readiness API — epoll, kqueue, IOCPOne thread · thousands of sockets

This is the crucial difference from fs.readFile(). For a file read, libuv hands the work to a worker thread, which blocks in read(). For network sockets, libuv does not need a worker thread, because the OS itself provides a way to ask:

"Of these N sockets I care about, which ones are ready right now?"

This is multiplexing.

Linux: epoll

▸ epoll-syscalls.txtcreate · ctl · wait
epoll_create()  → creates an epoll instance
epoll_ctl(fd)   → register a fd with the epoll instance
epoll_wait()    → block until any registered fd is ready

macOS / BSD: kqueue

▸ kqueue-syscalls.txtcreate · register · wait
kqueue()        → creates an event queue
kevent(...)     → register interest, or wait for events

Windows: IOCP

▸ iocp-model.txtcompletion-based
- different model: completion-based instead of readiness-based
- you submit operations; the kernel completes them and notifies you

libuv abstracts these differences. From Node's perspective: "register fd with libuv → libuv will tell me when something happens."

§ 37 · Wrong Mental Model vs CorrectEight common takes — and what's actually true

Wrong
Node spawns a thread per request.
Node uses ONE main JS thread for all requests. The OS readiness API lets that one thread handle thousands of sockets.
Wrong
Network I/O uses the libuv worker pool.
The worker pool is for fs, crypto, dns.lookup, etc. Network I/O uses epoll/kqueue/IOCP directly from the main JS thread.
Wrong
accept() blocks waiting for connections.
By the time Node calls accept(), the kernel has already completed the handshake and queued the connection. accept() returns immediately. The waiting was done by epoll_wait (or equivalent), not by accept itself, and even epoll_wait wakes the moment something is ready.
Wrong
req and res are different connections.
req and res are JS stream wrappers over the SAME underlying TCP socket. req is the readable side; res is the writable side; both reference one socket.
Wrong
res.end() guarantees the browser has received the data.
res.end() hands the bytes to the kernel send buffer. TCP delivers them, eventually. Node has no direct confirmation of browser receipt at the application layer.
Wrong
The HTTP parser is part of the OS or browser.
The HTTP parser is a Node-included library (llhttp) that runs in your Node process. The OS only knows about TCP bytes. HTTP is interpreted entirely in user space.
Wrong
server.listen blocks until a connection arrives.
server.listen returns almost immediately. It just sets up the listening socket and registers it with epoll. The 'request' callback runs much later, when actual connections occur.
Wrong
The handler runs in parallel for multiple requests.
Handlers run sequentially on the single main JS thread. What is parallel is the kernel's handling of TCP for many sockets. JS handlers interleave: one runs, returns or awaits, another can then run. They don't truly execute simultaneously.

§ 40 · The Full Invariant — Final Lock-this-inTen points · the whole model in a list

If you forget every diagram in this lesson, remember these ten lines. Each one collapses a section of the trace down to a single invariant.

▸ The full invariant
  1. The kernel owns and drives every TCP connection.
  2. libuv asks the kernel — via epoll/kqueue/IOCP — to be notified when any registered socket needs attention.
  3. When a notification arrives, the main JS thread reads bytes (or accepts a new connection).
  4. It feeds those bytes to llhttp.
  5. It builds req/res JS objects.
  6. It runs your handler.
  7. It writes response bytes back to the kernel.
  8. It returns to the event loop and sleeps in epoll_wait again.
  9. There is no request-per-thread. There is no spin-waiting. There is no busy polling.
  10. One thread, one event loop, and the kernel doing the heavy lifting.
!
Final lock-this-in
A Node HTTP server is fundamentally a TCP server with an HTTP parser bolted on top. server.listen(3000) registers and returns. req and res are stream wrappers over the same socket. Your handler runs on the main JS thread. res.end() hands bytes to the kernel — TCP and the kernel are responsible for delivery. That is the full browser HTTP request → Node server response story.
