DNS to keep-alive

Thirteen things happen.
Only one of them is your code.

A single HTTP request, from resolving a name to reusing the socket — ordered by when rather than by which layer owns what. The useful question at every step is not what transforms what, but what is already true at that moment: your handler is running and the body has not arrived; bytes are queued and none of them have reached the network.

You get the object first.
Everything else is decided for you.

The answer travelling the other way — from the res Node had already built before your handler was entered, to the socket going back in a pool. The useful question here is not what you wrote, but what was committed the moment you wrote it: the framing you never chose, the queue the bytes are actually in, and the event that says sent while the client has read nothing.

Every number on this page was measured, each from its own recorded run on v22.22.2: DNS and TCP against a real host, TLS against a local server with a self-signed certificate, read sizes and queue depths from instrumented servers, and keep-alive across 3 requests through one agent.

The response track was measured the same way, on the same build: framing captured off the wire in six variants, queue depths off a client that refused to read, the write coalescing counted at two levels of the same response, and the end-of-response ordering timestamped on one warm run.

The request timeline is an assembly — real durations from separate runs, composed onto one axis. The response timeline is a single warm run, which is why the three steps that could not happen in it are drawn on their own row rather than folded into the trace.

The deliberate gap in step 8 was 120 ms: the probe wrote the head, waited, then sent the body. A slow client produces the same shape without being asked.
