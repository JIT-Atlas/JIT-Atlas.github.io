Two stream object models — ReadableStream and stream.Readable

Two stream object models

WHATWG's ReadableStream and Node's stream.Readable are not two spellings of the same abstraction. One spreads a stream across four objects and refuses to let you read without taking a lock. The other puts every job on a single object that was an EventEmitter before it was a stream.

This walks the whole surface of both — the underlying source, the controller, the queue and its strategy, the reader, the lock, and on the other side _readableState, push(), flowing mode and destroy() — and then traces a reader and a generator side by side to show where the state actually lives.

Part one

The WHATWG object model

A stream, a controller, a reader and an underlying source — four objects, each with a small surface, and a queue that only one of them can touch.

The object shape

In browser and WHATWG terms, conceptually:

The public object you normally see is the one you constructed:

The important thing is that the source and the consumer are represented separately. That sentence is the entire design, and everything below is a consequence of it.

The tree above is not a teaching simplification of one big object. Those really are different objects with different prototypes, and you can count their members. Printed from a running process:

  • — handed to your source. The only door into the queue.
  • — owns and the state. Hands out readers.
  • — the consumer's handle. Takes chunks out, one promise at a time.

You are not subclassing anything. You hand the constructor a plain object literal and the stream keeps a private reference to it. Compare Node, where the source callback is a method on the stream — — which is why Node has you subclass or pass an options bag that gets installed onto the instance.

what returning a promise means, in each of the three

This is the part that is easy to skim and expensive to get wrong. All three callbacks may return a promise, and the promise means something different in each:

callbackreturning a promise means
startno pull until it settles — "open the file first"
pullno further pull until it settles — the re-entrancy guard
cancelreader.cancel() waits on your teardown

The middle one is the interesting one. A source that does slow asynchronous work cannot be re-entered while that work is in flight, and you get that guarantee by doing nothing except returning the promise you already had. Node's equivalent guard exists too — the reading flag — but it is invisible in the signature, and you satisfy it by eventually calling rather than by returning anything.

why the split exists at all

Because the stream object is public and the controller is not. Anyone holding the ReadableStream can cancel it or acquire a reader; only code running inside the source callbacks can put a chunk into it. In Node those two capabilities sit on the same object: whoever has the Readable can call both read() and push().

desiredSize is the backpressure signal

This is one of the most important pieces. Suppose:

1pull(controller) {
2 console.log(controller.desiredSize);
3}

desiredSize tells the underlying source how much additional data the queue wants, relative to its configured high-water mark. Conceptually:

it is a subtraction, not an estimate

The exact definition is highWaterMark − queueTotalSize. With a mark of 3 and a default size() of 1, enqueuing four chunks walks it straight down:

The negative value is not an error. Nothing stopped that fourth enqueue — the queue is simply over its declared capacity now, and the source is being told so. The mark is a request, in both object models.

This is how the WHATWG model connects demand to production:

WHATWG — demand reaches back to the source

Node in flowing mode — nothing asks

Rather than simply: the source emits, the consumer receives. The arrow starts in a different place, and that is the whole argument.

what actually drives the demand loop

Worth being precise, because "the consumer pulls" is slightly too romantic. Nobody in your code schedules pull. The stream calls it whenever two conditions hold: desiredSize is above zero, and no previous pull promise is still pending. Measured, with a mark of 3 and a pull that enqueues one chunk:

what happeneddesiredSize at the timestream's response

chunk enqueued2pull #2
chunk enqueued1pull #3
chunk enqueued0loop stops

Three pulls at construction, then silence, then one more pull caused by a single read. The consumer never called pull and the source never scheduled itself. Demand propagated.

The consumer side: getReader()

The consumer obtains a reader:

1const reader = stream.getReader();

The reader has the core operation:

1await reader.read();

which produces { value: chunk, done: false }, or eventually { value: undefined, done: true }. So the consumption loop is:

the fundamental pull interface
1while (true) {
2 const { value, done } = await reader.read();
3 
4 if (done) break;
5 
6 console.log(value);
7}

The consumer is explicitly asking: give me the next chunk. That is the fundamental pull interface.

why read() is a promise even when the data is already there

It is a uniformity decision, and it costs something. If two chunks are sitting in the queue, both reads resolve on a microtask rather than returning immediately — so a loop over a fully-buffered stream still yields to the microtask queue once per chunk.

What you buy is that the consumer's code has exactly one shape whether the data has arrived or not. Node made the opposite trade: is synchronous and returns null when it cannot be satisfied, which is fast but forces every consumer to handle two cases — and forces the API to add a 'readable' event to tell you when trying again is worthwhile.

releaseLock is sharper than it looks

Releasing while a read is outstanding does not silently abandon that promise, and it does not resolve it with done: true — which would be indistinguishable from a real end of stream. It rejects it:

Nothing was queued when that read was issued, so it was still pending at the moment the lock was released.

That is the kind of decision you only notice when it saves you. A consumer that hands off a stream mid-flight gets a loud failure rather than a phantom end-of-stream.

You cannot normally have this:

simultaneously, through ordinary readers. You can explicitly split it with instead.

what else quietly takes the lock

  • pipeTo() holds it for the duration of the transfer.
  • tee() holds it permanently — the original can never be read directly again.
  • for await...of holds it for the loop and releases it on exit.

And the reason Node has no equivalent is structural rather than an oversight: a Readable is an , and events are broadcast by construction. Two 'data' listeners both fire, and each chunk goes to both. Nothing in the object model can express "only one of you owns this", so single-consumption there is a convention you maintain rather than an invariant the API holds.

locked is also how you detect a spent stream

A ReadableStream from fetch() that has been read once cannot be read again, and the symptom is a TypeError from getReader() or from a second response.json(). If you need the body twice, it before the first read, or clone the Response.

pipeTo() and pipeThrough()

WHATWG streams make composition a first-class operation.

pipeTo — into a sink

1readable.pipeTo(writable);

pipeThrough — through a transform

1const out = readable.pipeThrough(transform);

This is analogous to Node's readable.pipe(transform).pipe(destination), but the underlying semantics are different.

the differences that actually bite

  • returns a promise. The transfer has an awaitable end, and a failure anywhere surfaces at that await. pipe() returns the destination, so there is nothing to await and nowhere for the failure to go.
  • Errors propagate by default. pipeTo forwards close, error and abort in both directions unless you opt out with preventClose, preventAbort, preventCancel. pipe() famously does not forward errors at all, which is why exists.
  • A TransformStream is literally two streams. Its whole prototype is constructor, readable, writable. So needs no machinery: it writes into one half and hands you back the other. Node's Transform is a single Duplex object with both sides folded into one.

tee()

tee() is particularly interesting. One source becomes two readable branches:

1const [a, b] = stream.tee();

The implementation coordinates the two consumers. That is a core part of the WHATWG stream abstraction, and there is no direct equivalent in Node's model.

the branches share a pull, not a queue

Measured: a source with highWaterMark: 1, teed, with only branch A read three times, still pulls 5 times from the source — because branch B's queue is filling and never draining. An abandoned branch grows without bound. Cancel the branch you do not want rather than dropping it.

Node's nearest equivalent, src.pipe(a); src.pipe(b), makes the opposite trade: backpressure comes from the slowest destination, so nothing grows unbounded, but one slow consumer throttles the other. .

The queuing strategy

The constructor can also receive a queuing strategy:

strategy as the second argument
1new ReadableStream(source, {
2 highWaterMark: 10,

4 return 1;
5 }
6});

The important abstraction is: the stream owns a queue whose size is interpreted through a queuing strategy.

the default is one chunk, and that surprises people

A ReadableStream with no strategy keeps exactly one chunk in hand. Not one kilobyte, not sixteen chunks — one. Two ready-made strategies change the unit:

strategysize(chunk) isqueue measured inNode's analogue
CountQueuingStrategy1chunksobjectMode: true, mark 16

So the two models do not differ in what they can express, they differ in what they assume. Node assumes bytes and a large buffer, because it was built for file and socket IO. The web API assumes counted chunks and a tiny buffer, because it was built to make backpressure the default rather than the optimisation.

Part three

Where they actually differ

Not push against pull. Both models can do both. The difference is which one the object model makes primary, and what it therefore refuses to let you do.

Who controls traversal

This is the key invariant.

WHATWG — the consumer asks, every time

1const reader = stream.getReader();
2 
3await reader.read();
4await reader.read();
5await reader.read();

Node in flowing mode — the stream delivers

1readable.on('data', chunk => {
2 // ...
3});

In the first, the consumer explicitly requests each next chunk. In the second, the stream machinery decides when data is emitted, and your callback runs whenever it does.

the consequence that is easy to miss

Attaching a 'data' listener is not an observation, it is a decision: it puts the stream into flowing mode and starts consumption. If you attach one to inspect a stream and then also await it elsewhere, the chunks are already gone.

The web model cannot be put in this position. Nothing flows until someone holds the lock and calls read(), and if a second consumer tries, they get a TypeError rather than half the data. .

But Node also has pull-like behaviour

This is where saying simply WHATWG pulls, Node pushes becomes too simplistic. Node has , and internally . So Node has a pull mechanism too:

paused mode, explicit reads
1readable.on('readable', () => {
2 let chunk;
3 
4 while ((chunk = readable.read()) !== null) {
5 console.log(chunk);
6 }
7});

Here the consumer explicitly calls read(). Node can operate in a non-flowing mode. The better distinction is this:

the distinction worth keeping

Node's Readable supports both flowing and paused consumption modes, while WHATWG's ReadableStream makes the reader/pull protocol the central consumption abstraction.

One is a superset of behaviours with a mode you select implicitly. The other is a single protocol you cannot opt out of.

Completion

The source eventually says no more. Both models let already-queued chunks drain first — neither discards on completion.

Node

1this.push(null);

That means EOF. Already-buffered chunks are still readable; only once the queue drains does 'end' fire.

WHATWG

1controller.close();

The stream moves to closed. Queued chunks still read out; only then does read() resolve { done: true }.

proof that close() does not throw the queue away

1const rs = new ReadableStream({
2 start(c) {
3 c.enqueue('a');
4 c.enqueue('b');
5 c.close();
6 }
7});
observed on Node v22.22.2
const rd = rs.getReader();
await rd.read(){ value: 'a', done: false }
await rd.read(){ value: 'b', done: false }
await rd.read(){ done: true }

Three reads, two chunks, one terminator. Node's behaves the same way, with two differences worth noting: it is the same method with a sentinel argument rather than a separate call, and the end arrives as an event ('end') rather than as a value in the result object.

That second difference is why 'end' can be missed entirely. If nothing is consuming — no listener, no resume(), no pipe — the queue never drains and 'end' never fires, even though the producer finished long ago. The web API cannot lose a terminator this way: done: true is the resolution of a read you asked for.

Errors

Node

1readable.destroy(error);

Or an internal failure. Either way the stream emits 'error', then 'close'.

WHATWG

1controller.error(error);

The stream enters errored. Pending and future reads reject, and desiredSize becomes null.

An 'error' event with no listener is special-cased by : it is re-thrown. A stream that fails while nobody is listening takes the process down. The web API's failure mode is the ordinary unhandled-rejection path instead, which is noisy but not fatal by default.

Cancellation

This is another major conceptual difference. WHATWG explicitly models cancellation:

1await reader.cancel(reason);

which ultimately reaches the underlying source:

1cancel(reason) {
2 // stop producing
3}

cancel — a message travelling upstream

destroy — a lifecycle command

Node's is broader. It is a resource and lifecycle termination primitive, not a message to the producer.

the direction is the whole point

cancel carries a payload the producer is expected to act on — abort the fetch, close the file handle, stop the timer. destroy carries an error or nothing, and the producer learns about it through _destroy(err, cb), which is a teardown hook rather than an explanation.

So Node has no first-class way for a consumer to tell a producer why it left. .

One subtle correction

A common one-line description goes: a source of chunks with a queue, a declared capacity, and a cancellation channel. That is a good conceptual description. Sharpened:

the sharper version

A WHATWG ReadableStream is a stateful byte or object stream abstraction with an internal queue, a queuing strategy that determines desired capacity, a controller through which the underlying source supplies data, and a reader through which a consumer requests data.

And the companion claim — Node's stream.Readable pushes rather than being pulled — should become:

the sharper version

Node's stream.Readable is a push-oriented, EventEmitter-based abstraction that also supports explicit read() consumption and internal _read() demand signalling.

That distinction matters, because otherwise you eventually hit readable.read() and think: wait, isn't Node supposed to be push? Exactly. Node isn't purely push. It has two consumption modes:

Node — two modes, one object

WHATWG — one protocol

Both ultimately have queues, backpressure, producers, consumers, completion, errors and cancellation. WHATWG streams are simply much closer to the iterator/pull side of the model than Node's classic flowing API is.

neither shape is the better one

  • The web shape is more ceremony and fewer sharp edges. You cannot read without taking the lock, you cannot produce without a controller, and backpressure is a number you have to look at rather than a boolean you can drop on the floor.
  • Node's shape carries fifteen years of ecosystem. Every file, socket, HTTP request and zlib transform in Node is a Readable. The web shape is what fetch() hands you.

Which is why the bridges matter more than the argument. .

The result is a promise, because WHATWG stream reads are asynchronous:

This is the exact opposite of Node's choice, where returns the chunk synchronously when the buffer can satisfy it, and null when it cannot.

The really interesting comparison

You now have await rd.read() and it.next(). They look superficially similar:

But the state lives in different places.

generator — the iterator owns the traversal state

next() means: resume this computation until its next yield.

stream — the stream owns the data, the reader owns the relationship

read() means: give me the next available chunk. It does not resume a suspended JavaScript function.

the crucial invariant

Generator. next() → resume computation → yield value → suspend computation.

ReadableStream. read() → consume from the stream queue → return chunk.

A generator's producer is the suspended function, and it cannot run while you are not asking. A stream's producer is independent, and it can and does run while you are not asking — which is exactly why a stream needs a queue, a capacity, backpressure and a cancellation channel, and a generator needs none of those.

Loop, iterator, stream

That leads directly into the progression:

And placed against each other, the three consumption shapes:

The generator is much closer to next value = resume my suspended computation, while a ReadableStream is next value = consume from an ongoing producer/queue. That is why a stream needs concepts a generator never does: queue capacity, backpressure, cancellation, a controller, locking, tee(), piping, and asynchronous arrival.

where a Node Readable sits on that ladder

On both rungs at once, which is the honest answer and the reason the comparison is worth making at all. It owns ongoing production and a queue like a stream, and it exposes a read() like an iterator, and it pushes like neither.

The one-line version to keep:

  • Generator — the producer is a suspended function. No queue, because it cannot run ahead of you.
  • ReadableStream — the producer is independent, and the only way to get a value is to ask a reader that holds an exclusive lock.
  • Readable — the producer is independent, and you may either ask or be told, on the same object, with no lock either way.

Part six

Crossing between them

The choice of model is not permanent, and the bridge is where the mismatches become visible.

toWeb and fromWeb

Node ships adapters in both directions:

4

Where you meet this: fetch() gives you a web ReadableStream as response.body, and most of the Node ecosystem still expects a Readable.

three things the bridge cannot carry across

  • Capacity units. A web stream counting chunks becomes a Node stream counting bytes. The numbers do not transfer, so a carefully tuned mark on one side means nothing on the other.
  • The lock. fromWeb takes it permanently; the original web stream is spent.
  • Where failure surfaces. An error arrives as a rejected read on one side and an 'error' event on the other — two different places in your code, with two different unhandled behaviours.

Byte streams, briefly

One piece of the web model has no Node counterpart at all. A stream constructed with type: 'bytes' can hand out a third kind of reader:

bring your own buffer
1const rd = rs.getReader({ mode: 'byob' });
2await rd.read(new Uint8Array(8));

The normal path has the producer allocate a chunk and hand it over. The BYOB path has the consumer allocate, and the producer fill it — one fewer allocation and one fewer copy per chunk. .

Node has no BYOB equivalent on stream.Readable. Its buffer-reuse story is solved a layer down: an fs read fills a pooled Buffer allocated by the runtime, and the chunk you receive is a view onto that pool.

ReadableStream

the stream object — what it owns and what it refuses to do

The stream is the thing that holds the queue and the state. Everything else in the web model is a handle onto it. Its own prototype is deliberately small:

printed from a running process
Object.getOwnPropertyNames(ReadableStream.prototype)constructor, locked, cancel, getReader, pipeThrough, pipeTo, tee, values

Notice what is absent: there is no read() on the stream. You cannot take a chunk out of a ReadableStream directly; you must first acquire a reader, and acquiring one locks the stream. That single omission is the whole consumer model expressed as an API shape.

What the stream keeps privately

These are specification-internal slots, not properties you can reach. The only one with a public reflection is the reader slot, exposed as the boolean locked.

the source's private door into the queue

You never construct a controller. It is handed to start and pull, and it is the only way the source can touch the queue. Five members, total:

Why separate it from the stream at all?

Because the stream object is public and the controller is not. Anyone holding the ReadableStream can cancel it or read it, but only code inside the source callbacks can put chunks into it. In Node the same two capabilities live on one object: whoever has the Readable can call both read() and push().

The byte-stream variant

A stream created with type: 'bytes' gets a ReadableByteStreamController instead, which adds byobRequest — a view the consumer supplied for you to write into directly.

ReadableStreamDefaultReader

the consumer's handle, and why it is a separate object

Five members, and one of them is a promise rather than a method:

ReadableStreamDefaultReader
Object.getOwnPropertyNames(ctor.prototype)constructor, read, releaseLock, closed, cancel
read() always returns a promise

Even when the chunk is already sitting in the queue. That is a deliberate uniformity: the consumer's code has one shape whether the data has arrived or not. Node makes the opposite choice — readable.read() is synchronous and returns null when it cannot be satisfied, which is why Node also needs the 'readable' event to tell you when to try again.

closed

Not an event and not a flag — a promise that fulfils when the stream closes and rejects when it errors. It gives you a place to await the end of the stream separately from reading it.

releaseLock during a pending read

The pending promise rejects with a TypeError. It is not left dangling and it does not quietly resolve with done, which would be indistinguishable from a real end of stream.

locked

the invariant that replaces coordination

locked is true from the moment a reader is acquired until it is released. While it is true, a second getReader() throws:

What else takes the lock
  • pipeTo() holds it for the duration of the transfer.
  • tee() holds it permanently — the original can never be read again directly.
  • for await...of holds it for the loop body and releases it on exit.
Why Node has no equivalent

Because a Node Readable is an EventEmitter, and events are broadcast by construction. Two 'data' listeners both fire; each chunk goes to both. Nothing in the object model prevents two consumers from believing they own the stream, so correctness there is a convention rather than an invariant.

tee()

and the memory cost nobody mentions

tee() locks the original and returns two branches that each see every chunk. The implementation reads once from the source and pushes into both branch queues.

The branches share one pull, but not one queue

Measured: a source with highWaterMark: 1, teed, with only branch A read three times, still pulls 5 times from the source — because branch B's queue is filling too and never draining.

the trap

If you tee a stream and abandon one branch, the abandoned branch's queue grows without bound for as long as the other branch keeps reading. Cancel the branch you do not want; do not just drop it.

Node's nearest equivalent

There isn't one in the object model. You pipe into two destinations — src.pipe(a); src.pipe(b) — and Node's pipe machinery applies backpressure from the slowest destination to the source, which is a different trade: no unbounded branch queue, but one slow consumer throttles the other.

What pipeTo does that a loop does not
  • It respects the destination's desiredSize, so backpressure crosses the join.
  • It forwards close, error and cancel in both directions unless you opt out with preventClose, preventAbort, preventCancel.
  • It takes the lock for the duration, so nothing else can interleave a read.

buffer and bufferIndex

the queue, as currently implemented

Node's queue was a linked list for years. In current Node it is a plain array with a read cursor:

Consumed slots are nulled so the chunk can be collected, and bufferIndex advances instead of the array being shifted. length is the byte total, not the slot count — which is why it drops by 2 and not by 1.

The web model's equivalent

A queue of { value, size } records plus queueTotalSize. Same idea, but you cannot reach it: there is no public property anywhere that exposes the chunks waiting in a ReadableStream. desiredSize is the only window, and it reports capacity rather than contents.

What size actually is

It is the high-water mark, and it is advisory — pushing more or less than size is legal. Compare with pull(controller), which passes no number at all and expects you to read controller.desiredSize if you care. Same job, opposite ergonomics: Node pushes the number at you, the web API makes you ask.

The re-entrancy guard

Node will not call _read again while a previous call has not yet pushed — the reading flag in _readableState guards it. The web API's equivalent guard is the promise returned from pull. Both exist for the same reason; only one of them is visible to you in the type signature.

Against controller.enqueue()

enqueue returns undefined. The web API refuses to overload the same call with a capacity answer and makes you read desiredSize instead. Practically: Node's version is one line shorter and easier to ignore, the web API's version is harder to ignore and impossible to ignore accidentally.

push(null)

The EOF signal. It is the same method with a sentinel argument, which is worth noticing — the web API spends a separate method, controller.close(), on it.

Attaching a 'data' listener starts consumption. If you attach one to inspect the stream and then also await it elsewhere, the chunks are already gone. The web API cannot be put in this position: nothing starts flowing until someone holds the lock and calls read().
