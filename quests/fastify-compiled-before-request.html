Source-level breakdown, fastify@5.12.5

Fastify, compiled before the first request.

The package is the wiring. The engines — avvio, find-my-way, ajv, fast-json-stringify — are imports. Every plugin scope is Object.create(parent), every schema becomes a function at boot, and a request is a fixed chain of ten hooks around one handler. This page walks the real files, runs a working model of the three engines in the page, and prints what it measured.

What is actually in the package

One file makes the instance; a directory of 32 files gives it behaviour; the engines live in 15 dependencies. Read the package as wiring: fastify.js assembles objects that other packages know how to run.

Each dependency owns one mechanism and exposes it through a small interface. avvio runs the plugin graph, find-my-way answers lookups, the two compilers turn schemas into functions, and pino and light-my-request sit at the edges.

How the packages compose at runtime

fastify() builds one object and hands parts of it to the engines. avvio gets the object to boot; find-my-way gets every route; each scope gets its own Request and Reply subclasses; each route gets a Context that holds its resolved hooks and compiled schema functions.

The magenta properties are the reason a value decorator added after a scope was created never reaches it: they are copied into the constructor when the subclass is built, not looked up on a prototype at request time.

Core modules

Every public method belongs to one file. Anything that builds or boots an instance lives in fastify.js and lib/plugin-override.js; anything about a route in lib/route.js; anything a request does in lib/request.js and lib/reply.js; anything about order in lib/hooks.js and lib/handle-request.js.

fastify.js, the factory

fastify(options) is the only export. It validates options against a generated schema (lib/config-validator.js), creates the root instance as a plain object with 69 own methods and properties, attaches avvio to it, builds the router, the root Request and Reply classes, the Hooks object and the SchemaController, and returns the object. Nothing listens, nothing is compiled yet.

lib/server.js, the listener

listen() first awaits ready(), then chooses how to build the Node server: http.createServer by default, https.createServer when https options exist, http2.createServer or http2.createSecureServer when http2: true, or whatever a serverFactory returns. The request listener it registers is the same function in every case.

lib/route.js and lib/context.js

route(opts) normalises the URL against the scope's prefix, runs onRoute hooks, creates a Context and inserts the route into find-my-way — all synchronously. Then it registers an after() callback and an avvio preReady listener: only there are the route's hooks resolved from the scope's arrays, its schemas compiled and its 404 context chosen.

  • prefix rules: / inside a prefixed plugin registers both /prefix and /prefix/; a leading slash is de-duplicated when the prefix ends with one.
  • HEAD: a GET route also registers a HEAD route unless exposeHeadRoute: false; its onSend hook measures the payload for content-length and drops it.
  • duplicates: the same method and path with the same constraints throws FST_ERR_DUPLICATED_ROUTE at registration.
  • Context: one per route, holding handler, schema, config, the resolved hook arrays, the compiled validators and serializers, and the errorHandler link.

lib/handle-request.js and lib/hooks.js

lib/hooks.js holds the ten lifecycle arrays and the runners. One generator, hookRunnerGenerator, produces the runner used by most stages: call the next function, and if it returns a thenable wait for it, else expect done(). Three stages get their own runner because they pass a payload through: preParsing, preSerialization and onSend.

lib/validation.js and lib/schema-controller.js

Schemas are plain objects until preReady. compileSchemasForValidation asks the scope's validatorCompiler (ajv by default) for one function per part — params, querystring, headers, body — and stores them on the Context. compileSchemasForSerialization does the same for each status code under response. The SchemaController holds the shared schemas added with addSchema and is copied per scope, so $refs resolve within the scope's view.

lib/four-oh-four.js, lib/error-handler.js, lib/errors.js

Not-found is a route: the 404 handler is stored as a wildcard context per prefix and runs through the scope's own hooks. Errors follow a chain built with Object.create, and every framework error is an instance created by @fastify/error with a stable code such as FST_ERR_VALIDATION.

lib/content-type-parser.js

Body parsing is a table keyed by media type. The defaults are application/json and text/plain; addContentTypeParser adds to the scope's copy of the table. A body with no matching parser is answered 415 before preValidation runs; an empty body with a JSON content type is 400 FST_ERR_CTP_EMPTY_JSON_BODY.

The three engines

Three mechanisms do the work: a boot graph that runs plugins in order and creates scopes, a radix tree that turns a method and path into a route context, and a hook chain that runs the context's functions in a fixed order around the handler.

The model that runs in this page

Every figure that steps through a boot, a lookup or a request is running in your browser: a re-implementation of those three engines, small enough to read. It is checked against the installed package by building the same application twice and comparing the responses and the observed call order.

Where it stops — read this before taking a figure as the whole truth:

  • No sockets: inject() is the only transport, so keep-alive, timeouts, HTTP/2 and onTimeout/onRequestAbort never fire
  • Schema support covers type, required, properties, additionalProperties, enum, const, min/max, length, pattern, items, $ref and default — not the full JSON Schema draft
  • Version constraints accept exact and x-wildcard forms rather than semver ranges
  • No logging: request.log is a no-op; the pino child-logger lifecycle is modelled in the figures, not run
  • Route-level errorHandler, schemaErrorFormatter and validatorCompiler/serializerCompiler options are not supported
  • bodyLimit is recorded but not enforced, and there is no streaming body — the whole payload is a string
  • Trailing-slash handling implements ignoreTrailingSlash and prefixTrailingSlash "both"; ignoreDuplicateSlashes is not modelled
  • Content-type parsers receive the whole body as a string; parseAs "buffer" behaves as "string"

Anything the model cannot do is either shown from captured output of the real package instead (the generated serializer, the log lines, printRoutes), or measured and labelled as such. No figure invents behaviour.

avvio, the boot graph

avvio is a queue with one rule: a plugin's own registrations drain before the next sibling starts. register appends, after appends a callback that runs when everything queued before it has loaded, and ready drains the root. Every plugin start goes through override, which decides whether a new scope is created.

  3. L5addHook for a lifecycle hook is itself deferred through after(): it lands at the end of this plugin's load and is pushed into claimRoutes, which already exists by then.
  4. L8ready() drains the root queue, emits preReady — hooks resolved per route, schemas compiled — then runs onReady hooks. After this, route, register and addHook throw.

find-my-way, the radix tree

Routes are inserted into a tree keyed by path characters, compressed so that a run of characters with no branch is one node. Lookup walks the tree with the request path and backtracks when a branch dead-ends. The page's model, FaLite, mirrors the priority and the backtracking; the real tree adds constraint stores, multi-parametric segments and a handler storage per method.

FaLite: the lookup walk
function walk(node, rest, params) {  if (rest.length === 0) return pick(node, method)  for (const child of node.statics) {    if (rest.startsWith(child.label)) {      const hit = walk(child, rest.slice(child.label.length), params)      if (hit) return hit    }  }  if (node.param) {    const seg = rest.slice(0, rest.indexOf('/') + 1 || rest.length)    const next = { ...params, [node.param.name]: seg }    const hit = walk(node.param, rest.slice(seg.length), next)    if (hit) return hit  }  if (node.wildcard) return pick(node.wildcard, method, { ...params, '*': rest })  return null}

  2. L3Static children first. Labels are compressed runs of characters, so /vouchers/ and /version share a /v node with two children.
  3. L9One parametric child per node, tried only after every static child failed — that is the whole priority rule, and it is structural rather than sorted.
  4. L14The wildcard consumes the rest of the path. The 404 contexts are stored on wildcard nodes, one per prefix.

Leaving the chain early

A hook that calls reply.send() ends the request: the remaining hooks of that stage and every later stage up to onSend are skipped, and onResponse still runs. Plugins and encapsulation

A plugin is a function of (scope, opts). Registering it queues it; running it creates a scope whose prototype is the parent's scope. Decorators, routes, hooks, schemas, parsers and the error handler added through that scope are private to it and to the scopes registered beneath it.

Lookup, priority and backtracking

At every node the order is fixed: static children, then the parametric child, then the wildcard. If a static branch matches the next characters but dead-ends further down, the walk returns and tries the parametric child from the same node — so /a/:x/c still answers /a/b/c when /a/b/d exists (measured). Route count does not change the walk: the number of nodes visited depends on the path, not on how many other routes exist.

Errors and not-found, per scope

Domain errors are classes with a status and a kind; the scope's error handler turns them into responses and rethrows everything else. onError at the root logs every error once, before any handler runs. The 404 is answered by the closest prefix: /vouchers/nope by the vouchers scope if it set one, otherwise by the root handler in app.js.

The final model

  • Boot is a queue of plugins drained depth-first; each plugin runs against a scope that is Object.create(parent).
  • Decorators publish through the prototype chain; a child sees the parent's, a sibling does not, and a load-time read sees only what has already loaded.
  • Hooks are arrays copied down at scope creation and pushed down afterwards; a route's arrays are fixed at preReady.
  • Schemas become functions at preReady: validators per part, a serializer per status.
  • Routing is one radix tree for every scope, prefixes joined at registration, 404 contexts per prefix.
  • A request is: lookup, ten stages around your handler, and one of three ways to answer.
  • Errors follow a second prototype chain of handlers, from the scope that failed up to the default.
